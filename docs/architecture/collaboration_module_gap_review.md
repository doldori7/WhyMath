### ①-c 이미 가동 중이고 **틀보다 엄격한 것** (갭으로 오인 금지)

- **분석 엔진은 초과충족**. 틀이 "성취도 분석·약점 분석"을 *기능*으로 요구하는 자리에, WhyMath는
  BKT·IRT 이중 추정과 그 합치 진단을 이미 갖고 있다: `l2/mastery_tracking.py:93` ·
  `l2/ability_tracking.py:24,68` · `l2/concept_diagnosis.py:71`(BKT↔IRT 합치) ·
  `l2/weak_concept_recommendation.py:147,245` · `l2/learning_path.py:143,247` ·
  `l2/prerequisite_recommendation.py`. 학생 1인칭 API `/v1/me/*` **29개**가 이를 이미 노출한다.
  → **기능 70-5·71-2·71-3의 갭은 "계산"이 아니라 "역할별 뷰"다.**
- **AI 과제 생성·AI 피드백도 초과충족**. L3 생성·사전생성(`l3/pregenerate/`)과 L4 코치·소크라테스가
  실재한다. 기능 74-2·74-8의 갭은 생성이 아니라 **배포 좌석**이다.
- **권한 모델이 틀보다 엄격**. 틀은 교사·학부모를 단순 상위 권한자로 그리지만, 정본은 **부모 가시성이
  학생의 부분집합**임을 매트릭스로 확정했고(`pipa_data_matrix.md:33-47`), `Role`을 `str` mixin 없는
  순수 `Enum`으로 만들어 `<`/`>` 비교가 `TypeError`가 되게 **구조적으로 봉인**했다
  (`schema/enums.py:1163`·`tests/backend/schema/test_role_enum.py` 동결).

### ①-d 정직 자인이 **이미 코드에 있는 곳** (갭 아님 — 트리거로 이관)

- `privacy/audit.py:11` — *"관리자접근(`record_admin_access_audit` — **현재 호출부 0곳**, 관리자 콘솔
  Phase B가 착지할 때 배선)"*. 실측 결과 실제로 호출부 0곳이다. **선언과 실태가 일치하므로 갭이
  아니다**(§4 트리거).
- `consent_grant.py` 도크스트링 — *"법정대리인이 어떻게 이 동의 화면에 접근/로그인하는가는 미해결이며,
  현재 동의-기록 엔드포인트는 **동의 대상 학생으로 인증된 세션**에서 호출된다"*. 즉 **"학부모"라는
  주체가 시스템에 존재하지 않음**을 코드가 스스로 밝히고 있다.
- `schema/enums.py:1164-1189` — `PARENT`/`TEACHER`/`SCHOOL_ADMIN` 미개설 사유와 개방 조건을 명시.

### ①-e 틀의 아키텍처와 정본의 차이 (판정의 전제)

틀은 협업을 **관리자 → 협업 계층 → AI Tutor → 학생**의 하향 계층으로 그린다:

```
        관리자 → [협업: 교사·학부모·그룹·토론·과제] → AI Tutor·Learning Analytics → 학생
```

정본은 협업을 *학생 위의 계층*이 아니라 **같은 코어 상태의 다른 뷰 + 그 사이의 권한 매트릭스**로 본다:

```
                    L1~L4 독립 수학 코어 (BKT·오개념·MasteryState — 단일 상태)
                                          │
        ┌─────────────────────────────────┼─────────────────────────────────┐
        ▼                                 ▼                                 ▼
   학생 뷰 (●)                      교사 뷰 (● ◐ ✕)                   부모 뷰 (◐ ✕)
   Flutter 학생앱                   별도 웹 (Phase 3+·B2B)          인앱 역할 레이어
        └──────────── pipa_data_matrix 9항목 × 3역할 항목 단위 인가 ────────────┘
                        (선형 서열 ❌ — 부모 ⊄ 학생의 상위집합)
```

이 차이가 판정을 가른다. 틀에서 "교사 대시보드"는 *새 기능*이지만 정본에서는 *기존 상태의 필터링된
투영*이다. 따라서 **협업 구축의 임계 경로는 화면이 아니라 매트릭스**이고, 그것이 D1이 최우선인 이유다.

## §3. 진짜 갭 설계

**실행 순서**: D1 → D2 → D3. D1이 최우선인 이유는 §0 ①-e가 보인 대로 **협업의 임계 경로가 화면이 아니라
매트릭스**이기 때문이다. D2가 D3보다 앞서는 이유는 **되돌릴 수 없음**이다 — 파기 누락은 사후에 고쳐도
이미 남은 데이터를 되돌리지 못한다.

### D1 — PIPA 권한 매트릭스가 문서 표로만 존재: 기계 강제 0 (최우선)

**증상.** `docs/legal/pipa_data_matrix.md` §2.4는 *"매트릭스의 각 칸을 코드의 **권한 체크 단위**로
사용한다"*고 **명령**한다. 실측: 매트릭스는 md 표로만 존재하고, 항목 단위 인가 코드·계약 파일·문서↔코드
동기 검사가 **하나도 없다**. 새 데이터 항목을 추가할 때 매트릭스에 행 추가를 강제하는 것도 없다.

**경로 4단 실측.**
1. `pipa_data_matrix.md:33-47` — 9항목 × 3역할 매트릭스(●/◐/✕)가 md 표로 존재.
2. `schema/enums.py:1191-1194` — `Role`은 `STUDENT`·`CONTENT_ADMIN` **2값**. 매트릭스의 "교사"·"부모"
   축에 대응하는 역할이 **없다**.
3. `api/_auth.py:96 require_role` — **역할 게이트만** 있고 *데이터 항목* 차원이 없다. 즉 현재 인가는
   1차원이다.
4. 매트릭스 9항목을 실제 산출물(L2 지표·`/v1/me/*` 응답 필드)에 매핑한 것이 **어디에도 없다** — "정답률"이
   어느 필드인지, "또래 비교"가 어느 API에 실릴 수 있는지가 코드와 무관하게 문서에만 있다.

**결론.** 매트릭스는 **선언은 정본, 집행은 0**이다. Phase 3에 `PARENT`/`TEACHER`가 열리는 순간 이 표를
사람이 읽고 손으로 지키는 것 외에 방어가 없다 — 미성년자 보호의 마지막 방어선이 **관례**에 의존한다.

**설계.**
- `data/access_matrix.json`을 **단일 진실원**으로 신설 — 9항목 × 역할축 × 해상도(`full`/`summary`/`none`)
  + 각 항목의 산출물 매핑(L2 함수 또는 API 필드).
- **새 추상 금지 — 선례가 정확히 동형으로 존재한다**: `data/render_contract.json` ↔
  `tests/backend/schema/test_render_contract.py`(+웹 `test/render_contract.test.js` 교차 게이트),
  `data/notation_contract.json` ↔ `tests/backend/l3/test_notation_contract.py`. 같은 패턴을 그대로 쓴다.
- 거버넌스 테스트: ⓐ 계약 ↔ `pipa_data_matrix.md` 표 동기 ⓑ `Role` enum 멤버 ↔ 계약 역할축 정합(역할이
  추가됐는데 계약 행이 없으면 red) ⓒ 선형 서열 금지 동결 승계 ⓓ 매핑 미정의 항목 검출.

**dead code 금지 충족.** 계약은 *코드*가 아니라 *불변식*이다 — 소비 좌석 없이도 유효하며, 오히려 좌석이
생긴 **뒤에** 만들면 늦다(그때는 이미 위반 코드가 존재한다). `render_contract.json`이 렌더러 없이도 계약인
것과 같은 논리. 이것이 §2-⑧의 "좌석 없는 역할은 만들지 않는다"와 충돌하지 않는 이유: **역할을 만드는 게
아니라, 역할이 만들어질 때 지켜야 할 계약을 미리 동결**하는 것이다.

**acceptance 변별력.** 계약의 임의 칸(또래 비교 × 부모 = `none`)을 `full`로 훼손 → **red 실측** → 복원 →
green. `Role`에 `PARENT`를 추가 → 계약 행 부재로 **red 실측** → 되돌림. 성공/실패에서 같은 값이 나오면
검증이 아니라 위장이다.

### D2 — 파기 계획 완전성 검사의 **방향이 반대**: 신설 테이블이 조용히 샌다

**증상.** `tests/backend/privacy/test_erasure.py:94 test_covers_all_planned_tables`는
`assert planned <= order`만 단언한다 — **계획 → 실행** 방향이다. 그 역방향(**실행 → 계획**: 사용자 소유
테이블 중 계획에 없는 것 검출)이 **없다**. 따라서 `user_id`를 가진 새 테이블은 `_ERASURE_PLAN`에 넣지
않아도 **아무도 red를 내지 않는다**.

**협업이 이 결함을 최악으로 밟는 이유.** 협업 테이블은 **다자 소유**다 — 교사가 만든 학급 안에 학생
데이터가, 그룹 노트 안에 여러 학생의 기여가 섞인다. 이는 현 구조의 근본 전제인 **"모든 사용자 데이터는
`user_id` 단일 소유 축"**(§0 ①-b)을 깨는 첫 사례가 된다. 그런데 학생 탈퇴 시 학급 기록·제출물·교사
코멘트를 어떻게 처리할지가 **어디에도 정의돼 있지 않다**. 지금 방향을 뒤집어 두면 협업 스키마가 착지할 때
부채가 **원천 차단**되고, 방치하면 "지우지 못하는 미성년자 데이터"가 조용히 생긴다.

**설계.**
- `Base.metadata.tables` 전수 → 소유 컬럼(`user_id`·`target_user_id` 등) 보유 테이블 중
  `_ERASURE_PLAN`·export 계획·retention 계획에 **누락된 것 검출 → red**.
- 예외는 **사유를 명시한 허용목록**으로만(감사 테이블처럼 계정 삭제 후에도 잔존해야 하는 것 —
  `privacy/audit.py`의 `user_id`가 FK가 아닌 이유와 같은 종류).
- **다자 소유 파기 규칙**을 협업 스키마 신설 *전에* 문서로 못박는다(누구의 삭제 요청이 무엇을 지우는가 ·
  타인 기여가 섞인 레코드의 처리 · 익명화 vs 삭제).

**acceptance 변별력.** `user_id`를 가진 더미 테이블을 임시 추가 → **red 실측** → 제거 → green.
동시에 **현행 62테이블에 이미 누락이 있는지 실측**한다(있으면 이 태스크 범위에서 상환, 없으면 그 사실을
기록 — 반증도 성과다).

### D3 — `daily_learning_metrics` 등 3테이블 writer 0: 배관만 있고 데이터가 없다

**증상.** `DailyLearningMetrics`·`UserBehaviorMetrics`·`ProblemSolveTimeDistribution`은
`db/models/timeseries.py:64,114,161`에 정의돼 있고 **파기·반출·보존 배관에 전부 등재돼 있다**
(`erasure.py:92` · `export.py:103` · `retention.py:55`). 그런데 **프로덕션 writer가 0건**이다 —
인스턴스화가 ORM/Pydantic 정의와 테스트에만 있다(실측 grep 0).

**이것이 왜 협업 리뷰의 갭인가.** 기능 71-4 "학습 시간 통계"와 70-5 "성취도 분석"의 **공급원이 바로 이
테이블들**이다. 즉 학부모·교사 리포트를 Phase 3에 만들려 해도 **채울 데이터가 없다**. 더 중요한 것은 이것이
선행 자매편 `visualization_module_gap_review.md` D1과 **동일 실패 유형**이라는 점이다 — *완비된 배관 +
미적재 공급원*. 그 편 §6이 재발방지로 등재한 패턴이 **다른 도메인에서 재발**하고 있다.

**협업을 기다릴 필요가 없다(좌석 근거).** 학습 시간·행동 집계는 **학생 1인칭에 지금 좌석이 있다** —
`/v1/me/*` 29개 엔드포인트가 Phase 1~2에 이미 가동 중이고, 학생 본인의 학습 시간은 매트릭스에서 **● 전체
공개**(#2 풀이 시간·#4 이용 시간대 모두 학생 본인 ●)다. 협업 리포트의 공급원을 **학생 축에서 선행 확보**하는
것이 순서상 옳다(부모·교사 뷰는 같은 데이터의 ◐ 투영일 뿐).

**설계.** 집계 잡 신설(기존 `learning_session`·`problem_attempt`·`attempt_event`에서 일별 롤업) +
학생 1인칭 조회 좌석. 새 인프라 금지 — 기존 활동 테이블과 기존 API 규약 재사용.

**acceptance 변별력.** 적재 전 `daily_learning_metrics` 행수 **0 실측** → 집계 실행 → **N행 실측**.
`/v1/me/*` 응답에 통계가 실제로 실리는지 라이브 확인(테이블만 차고 도달 0이면 viz D1의 재발이다).

### D4 — 정본 내부 Phase 모순 (태스크 아님 — 이번 작업에서 교정)

`07_community.md`가 교사 대시보드를 `:32`·`:41`·`:69`에서 **"Phase 3+"**로 적고, `:70`은 *"아래 Phase별
진입과 일치"*라고 **주장**한다. 그런데 `:100-108`의 Phase별 진입은 교사 대시보드·Live Problems를
**Phase 4**에 둔다. **`:70`의 "일치" 주장이 사실이 아니다.** `ROADMAP.md:177-179`는 M3.3(월 18~21)
교사 대시보드 베타 = **Phase 3**, `:133`도 역할 확장을 Phase 3으로 둔다.

**교정**: ROADMAP을 기준으로 `07_community.md` Phase별 진입에서 **교사 대시보드를 Phase 3으로** 옮긴다
(Live Problems·학교 콘텐츠 기여는 Phase 4 유지). 태스크 신설 없이 본 작업에서 직접 수정한다 — 문서 1곳의
사실 오류이고, 방치하면 협업 착수 시점 판단이 **정본에 따라 1개 Phase 어긋난다**.

## §5. 정직한 공백 — 이 리뷰가 답하지 않는 것

1. **다자 소유 데이터의 파기 규칙 자체**는 정하지 않았다. D2는 *누락을 검출하는 장치*를 등재할 뿐,
   "학생 탈퇴 시 그가 남긴 학급 제출물을 지울 것인가 익명화할 것인가"는 협업 스키마 설계 시점의 결정이며
   **변호사 검토 대상**일 수 있다.
2. **보호자 인증 방식**은 설계하지 않았다 — `MGMT-01`(변호사 자문)이 정본이고, 기계 대체 금지 대상이다.
3. **매트릭스 9항목이 충분한가**는 검증하지 않았다. 협업이 착지하면 "과제 제출 여부"·"학급 내 위치" 같은
   신규 항목이 생기며, 그때 §2.4대로 **행 추가 + 변호사 검토**가 필요하다.
4. **교사 웹의 IA·화면 설계**는 범위 밖이다(`docs/design/ui/03·04`가 정본이며 `ADMIN-*` 4태스크가
   **미등재**임은 `account_security_gap_review.md` 부록이 이미 기록).
5. **B2B 사업 조건**(학원 라이선스·학교 계약 형태)은 이 문서의 관할이 아니다.
6. **D3의 집계 주기·보존 기간**은 등재 태스크에서 정한다 — retention 계획에 이미 등재된 테이블이므로
   기존 보존 정책과의 정합을 그 시점에 확인해야 한다.
7. `07_community.md`의 **Live Problems Phase 배치**(4)와 ROADMAP(3)의 불일치는 D4에서 교사 대시보드만
   교정하고 **Live Problems는 손대지 않았다** — 갤러리·Live Problems의 Phase 판단은 `S4-12` 진척에
   달렸고, 근거 없이 정본을 옮기지 않는다.
