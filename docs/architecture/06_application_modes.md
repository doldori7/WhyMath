# L6. 응용 모드 (Application Modes)

> 동일한 7계층 코어 위에, 시장별 *진입점*만 다르게.

## 책임

같은 엔진을 *프롬프트·UI 레이어*로 분기. 7개 모드를 단일 코드베이스로 유지.

## 7개 모드

### 1. 학교 진도 모드 (학생 메인)
- **타깃**: 중1~고3 모든 학생
- **데이터**: 검정교과서 매핑 + 학교알리미
- **특징**: 학생 학교·학년 자동 매칭
- **Phase**: 2

### 2. 수능·내신 대비
- **타깃**: 고2~고3, N수
- **데이터**: 평가원 기출 + EBS 메타
- **특징**: 단계별 진단·약점 추적
- **Phase**: 2

### 3. 사고력·심화 (Phase 1 진입점!)
- **타깃**: 전 학년
- **데이터**: NRICH·Mathigon 영감 *오리지널*
- **특징**: 한국 *유일* 자원
- **Phase**: 1

### 4. 메타인지 코칭 (Phase 1 진입점!)
- **타깃**: 전 학년
- **데이터**: Polya·교수학·Kiki 기존 자산
- **특징**: 직접 활용 가능
- **Phase**: 1

### 5. 영재 트랙
- **타깃**: 영재교육원·KMO 준비
- **데이터**: KMO 디지털 자산·AoPS·MathNet
- **특징**: 객단가 높음 (월 49,900원)
- **Phase**: 3

### 6. 자유학기제 모드
- **타깃**: 중1 자유학기
- **데이터**: 사고력 + 게임화 (적정 수준)
- **특징**: B2B 학교 진입로
- **Phase**: 3~4

### 7. 디버깅 도장 (부가)
- **타깃**: 수학+코딩 융합 관심 학생
- **데이터**: 정보 교과 + 알고리즘
- **특징**: Phase 4+ 부가
- **Phase**: 4

## 자동 커리큘럼 정렬 — 모드 레이어 *위*

> MathScope PRD v1.1을 정본으로 흡수하며 들여온 정렬. 채택 근거는 `MEMORY.md` 2026-05-14 결정 로그 참조.

PRD의 **자동 커리큘럼 정렬**은 7개 모드와 *같은 층*이 아니라 *모드 레이어 위에 얹히는 한 단계*다. 모드가 "어느 시장 진입점인가"를 고른다면, 자동 커리큘럼 정렬은 그 위에서 "이 학생 한 명에게 어떻게 맞출 것인가"를 조정한다 — 어느 모드를 쓰든 항상 동작한다.

### 입력 — `StudentProfile`

L5 온보딩(국가·학년·학교·교과서·진도·목표, `05_interaction.md` 참조)이 모은 `StudentProfile`을 입력으로 받는다. 프로필 자체의 상태 관리는 L2 학습자 모델 책임.

### 7차원 자동 조정

정렬 엔진은 학생 프로필에 따라 다음 7가지를 자동 조정한다:

| # | 차원 | 조정 내용 |
|---|---|---|
| 1 | 활성 개념 풀 | 학생 교과서·진도에 등장한 개념만 활성, 미진도 개념은 잠금 |
| 2 | 표기 | 학생 교과서가 쓰는 기호·표기법 (예: 같은 개념의 출판사별 표기 차이) |
| 3 | 깊이 | 학년·목표에 맞춘 설명 깊이 (내신 대비 vs 사고력 심화) **— 1차 구현됨↓** |
| 4 | 풀이 스타일 순서 | 어떤 풀이 접근을 먼저 보일지 (학생 교과서 서술 순서 우선) |
| 5 | 용어 | 학생 교과서·학년 수준의 용어 선택 |
| 6 | 인접 개념 순서 | 다음에 이어질 개념의 제시 순서 (교과서 단원 배열 따름) |
| 7 | 평가 형식 | 내신형·수능형·서술형 등 목표에 맞춘 문항 형식 |

### 구현 현황 — 깊이 축(차원 3) 1차 소비 배선 (2026-06-30)

차원 3(깊이)의 *첫 런타임 소비 배선*이 학교 진도 모드에 들어갔다 — `curriculum_entry` Overlay
(L1·`required_depth`)를 실제로 읽어 깊이정렬을 한다(이 Overlay의 첫 소비처):
- **L1 read-time resolver**: `l1/curriculum/curriculum_resolve.py`(`CurriculumDepthResolver`) —
  concept_id → 한국(KR) `required_depth`를 단일 SELECT로 조회(`is_present`·country·NOT NULL 필터·
  N+1 0·sync 좌석). crosslink_resolve 패턴 동형.
- **L6 순수 깊이정렬**: `l6/school_progress/gating.py`(`curriculum_depth_alignment`) — 문항
  난이도가 그 개념의 요구 깊이(목표 난이도로 환산)에 맞을수록 우선순위 보너스(≤1.5·진도 겹침을
  압도하지 않는 품질 신호). 깊이 미주입 시 0.0 폴백(하위호환·데이터0 안전).
- **L5 결선**: `api/gating.py` — 문항→개념(problem_concept→concept) 조인 + resolver로 각 문항
  개념의 *가장 깊은* required_depth를 비영속 필드 `Problem.curriculum_required_depth`에 주입
  (성취기준 코드 주입과 동형 계약). 흐름: `HTTP → 후보 조회 → 개념코드 조인 → curriculum_entry
  resolver(to_thread) → 깊이 주입 → L6 깊이정렬`.

깊이는 *적격성 게이트가 아니라 우선순위 보너스*다(난이도처럼 — 깊이 불일치로 탈락시키지 않는다).
잔여(후속): 차원 1·2·4~7(활성 풀·표기·풀이 순서·용어·인접 순서·평가 형식)·다국(US/IMO)·
`required_depth` 큐레이션·표기/용어(notation_local·terminology_local) 소비.

#### 차원 1·6은 "전방 진도 경로" — L2 학습 경로와 다른 것이다 (2026-07-30 명시)

> 이 절은 오인을 막기 위해 있다. 저장소에는 **`학습 경로`라는 이름의 작동하는 좌석이 이미
> 있다**(`l2/learning_path.py` · `GET /v1/me/weak-concepts/{id}/learning-path`). 그것을 근거로
> "학습 경로는 구현됐다"고 판단하면 차원 1·6을 구현했다고 **오인**하게 된다. 둘은 다른 것이다.

| | 후방 결손 복구 경로 | 전방 진도 경로 |
|---|---|---|
| 질문 | "막힌 선수개념들을 *어떤 순서로* 되짚나" | "이 학생이 *다음에 배울* 개념은 무엇인가" |
| 소유 | **L2 학습자 모델** (`02_learner_model.md`) | **L1+L6 자동 커리큘럼 정렬** = 이 절의 차원 1·6 |
| 상태 | ✅ 실가동 | 🔴 코드 0 (위 잔여 목록) |

**차원 6의 *정밀* 정렬(출판사별 페이지 순서)은 여전히 입력 데이터가 없어 착수 불가다.** 실측
(2026-07-30): `introduced_grade`·`grade_band`는 적재되지만 그것은 학년 밴드이지 **단원 배열이
아니다**. 차원 6이 명시적으로 요구하는 "교과서 단원 배열"은 — `textbook_mapping` 테이블이
**스키마·ORM만 있고 적재기 0** · `data/corpus/units_v1/`는 **소단원 DSL 파일럿 1건**
(`quadratic_maxmin.unit.yaml`) · `curriculum_entry.textbook_unit_refs` 배열은 로더가 채우지 않음 ·
그리고 `curriculum_entry`에 **순서를 담을 정수 필드 자체가 없다**(그룹 3 시점 = `introduced_grade`·
`grade_band`·`effective_from`뿐). 이 정밀 정렬의 착수 선결 조건은 ①단원 배열 데이터 확보
②`sequence` 계열 스키마 확장이며, 그 전에 경로 생성기를 만들면 빈 입력 위의 가짜 정밀도가 된다.

⚠️ **2026-07-30 부분 정정 — coarse 기본 순서는 이미 가능하다.** 위 미비는 `curriculum_entry`
Overlay 한정이다. **성취기준 원본(`standards_v1`)의 코드 자체가 22개 고등 과목 전부에서
`[과목-단원번호-소단원번호]` 구조로 이미 파싱**된다(예: `12미적Ⅰ` 3단원 — 함수의 극한과 연속→
미분→적분). 이건 **국가교육과정 자체의 구조**(출판사 무관)라 즉시 쓸 수 있고, 학생의 학년트랙·
과목·단원·소단원 진행 위치를 국가교육과정 기본 순서로 보여주는 브레드크럼(`GET /v1/me/
curriculum-position`)은 이 데이터로 착수한다(D10·D11). **다만 이것은 출판사별 정밀 대체가
아니다** — 학교별 진도 속도·교과서 페이지 순서의 미세한 차이는 여전히 모르며, 그 정밀 정렬만
위 데이터 차단에 걸린다.

상세 대조·불채택 근거: `learning_path_module_gap_review.md` §0·§4-1·§4-2·§5-1·D10·D11.

### 모드와의 결합

자동 커리큘럼 정렬과 7개 모드는 **직교**한다 — 곱집합으로 동작한다:

- **모드**가 콘텐츠 *풀과 교수학 가중치*(`ModeConfig`의 `content_filter`·`polya_emphasis` 등)를 정한다.
- **자동 커리큘럼 정렬**이 그 풀 위에서 *이 학생의 교과서 좌표에 맞춘 7차원 조정*을 한다.
- 예: 같은 "학교 진도 모드"라도 미래엔 교과서 학생과 천재교육 교과서 학생은 표기·풀이 순서·인접 개념 순서가 다르게 정렬된다.
- 예: 한 학생이 "사고력 모드"와 "수능·내신 모드"를 오갈 때, 모드는 바뀌어도 그 학생의 교과서·진도 기반 7차원 조정은 일관되게 유지된다 (코어 상태 공유 원칙과 같은 결).

### 경계 (7계층)

- 정렬 **엔진**은 L1(다국 커리큘럼 매트릭스·교과서 매핑 파이프라인)+L6(모드 위 조정 레이어) 책임.
- 정렬의 **입출력 UI**(온보딩·교과서 좌표 메인 화면)는 L5 책임 (`05_interaction.md`).
- `StudentProfile`·`MasteryState`의 상태 관리는 L2 책임.
- L6은 L1을 호출해 매핑 데이터를 받고, L2의 프로필을 읽어 조정한다 — 정렬에 쓰이는 데이터·모델을 *구현하지 않는다*.

## 모드 분기 패턴

```python
class ApplicationMode(str, Enum):
    SCHOOL_PROGRESS = "school_progress"
    EXAM_PREP = "exam_prep"
    THINKING = "thinking"  # Phase 1 진입
    METACOGNITION = "metacognition"  # Phase 1 진입
    GIFTED = "gifted"
    FREE_SEMESTER = "free_semester"
    CODING_DOJO = "coding_dojo"

class ModeConfig(BaseModel):
    """모드별 설정"""
    mode: ApplicationMode
    
    # 콘텐츠 풀
    content_filter: dict      # 어떤 콘텐츠 추출할지
    
    # 교수학 가중치
    polya_emphasis: float     # 0~1
    metacog_freq: float       # 메타 프롬프트 빈도
    
    # 정서·게이미피케이션
    gamification_level: int   # 0(없음) ~ 3(중간), 4+ 금지
    
    # 비용·티어
    # 명칭 충돌 해소(2026-05-20, docs/architecture/03a_l3_router_design.md §0.1): 구 LLMTier 단일 enum이
    # 두 축으로 분해됨. 모드 기본값은 *비용·위치 축*(축1)만 정한다 — 로컬 모델 크기(축2 FAST/MID/QUALITY)는
    # 모드가 아니라 요청별 신호로 L3 라우터가 결정.
    default_cost_tier: CostTier  # 구 default_llm_tier: LLMTier → CostTier(LOCAL/CLOUD_MID/CLOUD_HIGH)
    daily_cost_limit_won: int
    
    # UI
    primary_color: str
    ui_layout: str
```

## 진입 순서 (Phase별)

```
Phase 1: 사고력 + 메타인지 (한국 빈자리)
   ↓
Phase 2: + 학교 진도 + 수능 (메인 매출)
   ↓
Phase 3: + 영재 (프리미엄)
   ↓
Phase 4: + 자유학기 (B2B 진입로)
   ↓
Phase 4+: + 디버깅 도장 (부가)
```

## 단일 앱 모드 분기 유지 (PRD 3개 앱 분리는 반려)

> MathScope PRD v1.1을 정본으로 흡수하며 정렬한 입장. 채택 근거는 `MEMORY.md` 2026-05-14 결정 로그 참조.

PRD는 **학생용·교사용·학부모용 3개의 별도 앱**을 제안한다. WhyMath는 이를 **채택하지 않는다**. 대신:

- **Flutter 단일 학생앱 + 모드 분기**를 유지한다 (슬라이스 89) — 학생·학부모 역할은 7개 모드와 같은 분기 메커니즘으로 동일 코드베이스 안 UI·권한 레이어로 가른다. **교사 대시보드만 별도 웹(React/Next)으로 분리**(시험지 빌더·SEO는 PC 웹 작업·Phase 3+) — 'PRD의 3개 병렬 앱'이 아니라 독립 코어를 공유하는 도구 웹.
- **교사·학부모 대시보드는 Phase 3+에 도입**한다 (`07_community.md` 참조). Phase 1~2는 학생 경험에 집중.

**반려 근거**:

- 4~5명 팀이 3개 앱을 동시 개발·유지하는 것은 명백한 과부하 — `MEMORY.md` 폐기 패턴 "처음부터 풀 K-12"와 같은 범위 폭발 리스크.
- WhyMath의 7계층 코어는 이미 단일 코드베이스 위 모드 분기로 설계됨 — 역할 분기도 같은 패턴으로 흡수 가능하므로 앱을 쪼갤 구조적 이유가 없다.
- 코어 상태(BKT·오개념·`MasteryState`) 공유가 단일 앱에서 자연스럽다 — 학생·교사·학부모가 *같은 학습 데이터의 다른 뷰*를 보는 구조이므로, 앱을 나누면 오히려 동기화 비용만 늘어난다.
- 의사결정 우선순위(CLAUDE.md): 개발 속도(7번)보다 학습 효과(4번)·UX(5번)가 우선이며, 3개 앱 분리는 *어느 가치도 더 주지 못하면서* 개발 부담만 키운다.
