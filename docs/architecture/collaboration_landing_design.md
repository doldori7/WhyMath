## §1. 왜 지금 "설계만" 하는가 — 순서가 뒤집히면 안 되는 이유

틀은 협업을 **"1단계"**로 적었다. 정본은 **Phase 3+**다. 이 차이는 일정 취향이 아니라 **선결 조건의
귀결**이며, 갭 리뷰가 이미 반려했다. 이 문서는 그 반려를 승계하되, 반려로 끝내지 않고 **선결 조건을
지금 앞당겨 깐다**.

| 선결 조건 | 현 상태 | 지금 가능한가 |
|---|---|---|
| `PARENT`·`TEACHER` 역할 좌석 | 미개설(의도) | ❌ 좌석 없는 역할 = dead code |
| 법정대리인 실 본인확인 | `MGMT-01` **blocked**(변호사 자문) | ❌ 법령 유래 절차 — 기계 대체 금지 |
| `ConsentScope` 제3자 제공 범위 | `service_core` 1값 | ❌ `MGMT-02` 회신 전 확장 금지 |
| 조직(학교·학원·반) 테넌시 | 0 (`school_id`는 FK 없는 나대지 컬럼) | ❌ B2B 계약 전 |
| **권한 매트릭스 집행 계약** | 선언만(md 표) · 집행 0 | ✅ **`COLLAB-01`** |
| **파기 완전성 검사 방향** | 계획→실행 단방향 | ✅ **`COLLAB-02`** |
| **다자 소유 파기 규칙** | **없음** | ✅ **본 문서 §3** |
| **보호자 접근 모델(공학 축)** | 없음 | ✅ **본 문서 §4**(법무 축은 분리) |
| **매트릭스 확장 항목** | 9항목 고정 | ✅ **본 문서 §5**(추가는 변호사 검토 후) |

**핵심 논리**: 규칙·계약은 *코드*가 아니라 *불변식*이다. 소비 좌석이 없어도 유효하며, 오히려 좌석이
생긴 뒤에 만들면 늦다. `data/render_contract.json`이 렌더러 없이도 계약인 것과 같다. 이것이
"좌석 없는 역할은 만들지 않는다"와 충돌하지 않는 이유 — **역할을 만드는 게 아니라, 역할이 만들어질
때 지켜야 할 규칙을 미리 동결**하는 것이다.

## §2. 협업 도메인의 소유 축 — 현 구조가 깨지는 지점

### 2.1 현 전제: 모든 사용자 데이터는 `user_id` 단일 소유 축

현행 **62테이블**(`db/models/*.py` `__tablename__` 전수)은 예외 없이 이 축 위에 있다. 그래서 삭제권
행사가 단순하다 — `_ERASURE_PLAN`의 child→parent 순서로 `user_id` 일치 행을 지우면 끝이다
(`privacy/erasure.py`).

협업 엔티티는 이 전제를 **처음으로 깬다**. 학급 안에 여러 학생 데이터가, 과제 제출물에 학생 기여와
교사 코멘트가, 그룹 산출물에 다수 학생 기여가 섞인다. **"학생 A의 삭제 요청이 무엇을 지우는가"가
자명하지 않게 된다.**

### 2.2 소유 축 5분류

협업 착지 시 생길 모든 테이블을 아래 5형 중 하나로 **반드시** 분류한다. 분류 없는 협업 테이블 신설은
금지한다(§3의 처리 규칙이 형별로만 정의되므로, 미분류 테이블은 파기 규칙이 없는 테이블이다).

| 형 | 정의 | 협업 예시 | 기존 선례 |
|---|---|---|---|
| **A** 학생 단독 소유 | `user_id` 단일 소유 축 | 학생의 과제 제출 답안·시도 로그 | 현행 62테이블 전부 |
| **B** 학생 기여 + 타인 컨테이너 | 컨테이너는 타인(교사·조직) 소유, 그 안에 학생 기여가 행으로 존재 | 학급 명단 멤버십 · 제출물의 교사 코멘트 · 그룹 산출물 기여 | **없음(신규)** |
| **C** 교차 사용자 집계 | 다수 사용자에서 산출되나 **개인 재식별 불가** | 학급 평균 숙달도 · 문항별 정답률 | `ProblemSolveTimeDistribution`(`timeseries.py:114`) |
| **D** 조직 소유·학생 데이터 미포함 | 교사·조직의 저작·설정 | 학급 정의 · 과제 정의 · 문항세트 구성 | 콘텐츠 테이블(문항·개념) |
| **E** 감사 | 계정 삭제 후에도 법적 증빙으로 잔존 | 동의 이력 · 반출 감사 | `privacy_audit`·`deletion_audit`(`user_id`가 FK 아님) |

> **C형이 왜 중요한가.** 갭 리뷰 초판은 `ProblemSolveTimeDistribution`을 파기 배관 누락으로 오인했다
> (2026-08-04 정정). 실제로는 `export.py:16-17,76-77`이 **"`problem_id` 키 교차 사용자 집계라 개인
> PII가 아니므로 영구 제외"**라고 명시한 **의도된 제외**다. 즉 저장소에는 이미 "개인 소유 축 밖의
> 데이터" 판례가 **하나** 있었고, 협업의 C형은 그 판례의 확장이다. 새 원칙을 발명하는 게 아니다.

## §3. 다자 소유 파기·반출·보존 규칙 v1

> 갭 리뷰 §5-1 공백 해소. `COLLAB-02` acceptance ⑤가 요구하는 문서가 **이 절**이다.

### 3.1 형별 3배관 처리표

| 형 | 파기(`erasure.py`) — 학생 A 삭제 요청 시 | 반출(`export.py`) — 학생 A 요청 시 | 보존(`retention.py`) |
|---|---|---|---|
| **A** | **행 삭제** | **전량 포함** | 기존 `pii_retention_years` |
| **B** | **기여 행 삭제**(컨테이너는 잔존). 컨테이너의 집계 필드는 재계산 | **본인 기여분만**. 타인 기여·타인 식별자 **제외** | 컨테이너 소멸 시 종속 삭제 + PII 축은 기존 기간 |
| **C** | **삭제하지 않음**(재식별 불가 전제). 단, A 이탈 후 **재계산 대상**에서 제외 | **제외**(개인 PII 아님 — 기존 판례 승계) | 조직 축 기간 |
| **D** | **삭제하지 않음**(학생 데이터 미포함) | **제외** | 조직 축 기간 |
| **E** | **삭제하지 않음**(법적 증빙) | 반출 대상 여부는 항목별(현행 규약 승계) | 법정 보존기간 |

### 3.2 B형의 판정 기준 — "익명화로 충분한가"

B형에서 *컨테이너를 남기고 기여만 지우는* 처리는 **기여가 익명화로 실제 재식별 불가가 될 때만**
정당하다. 판정 기준 3개를 **모두** 통과해야 한다.

1. **구조화 기준** — 기여가 구조화 데이터인가(정오·단계 검증 결과·선택지·수식 AST). **자유 텍스트는
   실패**한다: 문장은 그 자체가 준식별자이며(문체·오타·맥락), 식별자 컬럼만 지워도 재식별 위험이
   남는다.
2. **소집단 기준** — 컨테이너 구성원 수가 작으면(학급·팀) 잔존 기여의 **위치만으로 개인이 특정**된다.
   "3인 팀에서 2명의 기여가 남으면 나머지 1명이 누구인지 자명"하다. → 소집단에서는 익명화가 아니라
   **삭제**.
3. **역산 기준** — 잔존 데이터로 삭제된 개인의 값을 **역산할 수 없어야** 한다. 컨테이너 집계(합계·
   평균·인원수)를 그대로 두면 삭제 전후 차분으로 개인값이 복원된다. → 집계는 **반드시 재계산**한다.

> **이 기준이 기능 미채택과 정합하는 지점**: 갭 리뷰 §2-①이 협업 화이트보드·그룹 채팅·질문 게시판·
> 댓글을 *"미성년자 간 자유 텍스트 + 모더레이션 인력 0"*을 이유로 미채택했다. 이 절은 **두 번째
> 독립 사유**를 추가한다 — 자유 텍스트는 기준 1을 통과하지 못하므로 **삭제권 행사 시 지울 수도,
> 남길 수도 없다**. 즉 자유 텍스트 협업의 미채택은 운영 여력 문제만이 아니라 **파기 가능성 문제**다.
> 인력이 생겨도 이 사유는 사라지지 않는다.

**따라서 채택 가능한 B형은 구조화 기여로 한정된다** — 과제 제출의 정오·단계별 막힘 지점·풀이 AST.
이는 §6의 착지 형태를 직접 규정한다.

### 3.3 삭제 방향의 비대칭 — 누구의 요청이 무엇을 지우는가

| 요청자 | 대상 | 결과 |
|---|---|---|
| 학생 A | 본인 계정 | A의 A형 전량 삭제 + B형 기여 삭제(§3.2) + 컨테이너 집계 재계산. **컨테이너·D형 불변** |
| 교사 | 본인이 만든 학급(D형) | 컨테이너 삭제 시 종속 B형 **동반 삭제**. 학생의 A형(개인 학습 이력)은 **불변** — 학급은 컨테이너일 뿐 학생 데이터의 소유자가 아니다 |
| 교사 | 학생 개인 데이터 | **불가**. 교사에게 학생 데이터 삭제 권한은 없다(매트릭스에 삭제 권한 축 자체가 없음) |
| 조직(학교) | 계약 종료 | D·C형 처분은 계약 조건. **학생 A형은 학생 소유로 잔존** — B2C 계정이 B2B 계약에 종속되지 않는다 |

**원칙**: *컨테이너 소유권은 내용물 소유권이 아니다.* 학급이 사라져도 학생의 학습 이력은 학생 것이다.
이는 B2B 확산 시 "학원이 학생 데이터를 가져간다"는 형태를 구조적으로 차단한다.

### 3.4 변호사 검토가 필요한 지점 (기계 판단과 분리 — 단정 금지)

아래는 **공학이 정할 수 없는** 것이다. `MGMT-02` 자문 항목에 포함시켜야 한다.

1. **B형 기여의 익명화 잔존이 PIPA상 "파기"로 인정되는가** — §3.2 3기준 통과가 법적 파기 요건을
   충족하는지. 미충족이면 B형은 전부 삭제 방향으로 바뀐다.
2. **교사·조직에 대한 학생 데이터 제공이 "제3자 제공"인가 "처리 위탁"인가** — 동의 형태와
   `ConsentScope` 값이 달라진다(`pipa_data_matrix.md` §5 미체크 항목).
3. **부모 보고서 제공이 제3자 제공에 해당하는가** — 법정대리인이라도 별도 검토 대상으로 이미 등재됨.
4. **계약 종료 시 조직 축 데이터의 처분 의무 기간**.

> 이 4건은 **답이 나올 때까지 코드로 단정하지 않는다.** §3.1 표는 답이 도착하면 갱신되는 초안이며,
> `COLLAB-02`가 동결하는 것은 표의 *내용*이 아니라 **"모든 협업 테이블은 5형 중 하나로 분류되고
> 3배관 각각에 처리가 지정돼 있어야 한다"는 구조적 요건**이다.

## §4. 보호자 접근 모델 — 3안 비교와 권고

> 갭 리뷰 §5-2 공백 해소. 갭 리뷰는 이 항목을 "`MGMT-01`이 정본이고 기계 대체 금지 대상"이라며
> 설계하지 않았다. **그 판단은 절반만 옳다** — 본인확인 *방식의 법적 적정성*은 법률 판단이지만,
> **보호자가 어떤 좌석으로 접근하는가는 공학 결정**이다. 둘을 섞어 두면 법무 회신이 도착해도 설계를
> 처음부터 시작하게 된다. 이 절은 둘을 분리한다.

### 4.1 현 상태

`consent_grant.py`의 `GuardianVerifier` Protocol + `StubGuardianVerifier`(`method="stub"`)가 있고,
`POST /v1/users/me/parental-consent`는 **동의 대상 학생으로 인증된 세션**에서 호출된다. 즉 시스템에
**"보호자"라는 주체가 존재하지 않는다** — 코드가 스스로 그렇게 밝히고 있다. 기능 플래그
`parental_consent_grant_enabled`는 prod 기본 off다(stub만으론 미성년 self-consent 우회 가능).

### 4.2 3안 비교

| 신규 PII 수집 | 0 | 보호자 이메일·본인확인 정보 | 0(기존 `guardian_email_hash`) |
| `MGMT-01` 의존 | 낮음(현재도 stub) | **높음** — 계정 = 신원 | 중간 |
| 상시 열람(감시) 위험 | — | **높음** — 대시보드는 상시 접근 | **낮음** — 주기 요약 1회성 |
| 학생 통제권 | 없음 | 연결 승인·해제 | **발급 거부·즉시 무효화** |
| 알림 인프라 필요 | 불필요 | 필요 | **필요**(이메일 최소) |

| 유출 리스크 | — | 계정 탈취 | **링크 유출** → TTL·1회성으로 완화 |

### 4.3 권고 — Phase 3 = ⓒ, Phase 4 = ⓑ (조건부)

**정본이 요구하는 것은 "상시 대시보드"가 아니라 "주 1회 보고서"다.** `07_community.md`는 학부모
컴포넌트를 *주 1회 푸시·학생 동의 시·비교/랭킹 ❌*로 규정하고, `pipa_data_matrix.md` §2.3은 부모에게
**"감시 도구가 아니라 지원 도구"**를 준다고 못박는다. 틀의 "학부모 대시보드"(71)를 **상시 조회
화면**으로 읽으면 정본과 충돌하지만, **주기 요약 전달**로 읽으면 충돌하지 않는다.

ⓒ가 이 의도와 가장 정합한다:

- **투영 시점 고정** — 링크에 담기는 것은 *쿼리 권한*이 아니라 **이미 매트릭스로 필터링된 정적
  요약**이다. 보호자 측에 조회 API가 열리지 않으므로, 매트릭스 위반 경로가 구조적으로 생기지 않는다.
- **최소 권한** — 보호자는 열람만 한다. 학생 데이터에 대한 수정·삭제·타 학생 조회 표면이 0이다.
- **학생 통제권** — 학생이 발급을 거부하거나 기존 링크를 즉시 무효화할 수 있다(정본의 "학생 동의 시").
- **`MGMT-01` 의존 완화** — 링크는 "동의를 받은 보호자 이메일로만" 발송되므로, 본인확인의 강도가
  계정 발급만큼 요구되지 않을 **가능성**이 있다. (이 완화가 법적으로 성립하는지는 §3.4와 함께 자문
  대상 — 단정하지 않는다.)

**ⓑ는 B2B·다자녀 시점에 필요해진다** — 자녀가 둘 이상이거나 보호자가 학원과 계약 주체가 될 때
링크 방식은 관리가 무너진다. 그때 ⓑ로 확장하되, **ⓒ의 투영 계층을 그대로 재사용**한다(보호자
계정이 생겨도 조회하는 것은 여전히 매트릭스로 투영된 요약이지 원자료가 아니다).

## §5. 매트릭스 확장 후보 항목 — 협업이 만들어내는 신규 데이터

> 갭 리뷰 §5-3 공백 해소. `pipa_data_matrix.md` §2.4는 **"새 데이터 항목 추가 시 반드시 행을 추가하고
> 변호사 검토를 거친다"**고 명령한다. 아래는 **초안 판정**이며, 등재는 검토 후다.

### 5.1 신규 항목 기본값 원칙 — deny by default

**신규 항목의 기본값은 전 역할 ✕이고, ●·◐로 여는 쪽이 근거를 댄다.** 현행 9항목이 이미 "부모 열에
✕·◐가 많은" 형태인 이유(§2.3 불안의 압박 전이 차단)가 신규 항목에도 그대로 적용되기 때문이다.

### 5.2 초안

| # | 항목 | 학생 | 교사(B2B) | 부모 | 근거 |
|---|---|:-:|:-:|:-:|---|
| 10 | 과제 제출 여부·시각 | ● | ● | ◐ | 교사 지도에 필수. 부모는 *수행 여부*만(시각 원자료는 #4 이용 시간대 ◐ 승계) |
| 11 | 미제출 누적 | ● | ◐ | ◐ | 압박 전이 위험 → 양쪽 요약. 연속 미제출 강조 표현 금지 |
| 12 | 단계별 막힘 지점(PRM) | ● | ◐ | **✕** | #3 오답 패턴의 확장 — **부모 미공개 승계**. 교사는 지도용 요약 |
| 13 | 교사 코멘트 열람 여부 | ● | **✕** | ✕ | *열람 감시*는 지도 정보가 아니다. 교사에게도 닫는다 |
| 14 | **학급 내 상대 위치** | **✕** | **✕** | **✕** | **항목 자체를 산출하지 않음** — §5.3 |
| 15 | **그룹 기여도·참여도** | **✕** | **✕** | **✕** | **항목 자체를 산출하지 않음** — §5.3 |

### 5.3 14·15를 "전 역할 ✕"이 아니라 "미산출"로 두는 이유

또래 비교(#8)는 학생 본인조차 ◐이고 부모는 ✕다. **학급·팀은 N이 작다** — 소집단 순위는 개인 순위를
직접 노출하거나(N=20이면 "3등"은 곧 개인 식별) 역산 가능하게 한다. 갭 리뷰 §2-⑥이 팀 성과·참여도
순위를 **영구 미채택**으로 판정한 근거가 이것이다.

따라서 14·15는 권한을 ✕로 *설정*하는 게 아니라 **계산 자체를 하지 않는다**. 권한 설정은 코드 실수로
뚫릴 수 있지만, 산출하지 않는 값은 새어 나갈 수 없다. 이는 `Role`을 `str` mixin에서 이탈시켜 서열
비교를 `TypeError`로 봉인한 것과 같은 계열의 **구조적 방어**이며, `anti_gamification_governance_test`
계열 게이트가 식별자 수준에서 물리적으로 막는다.

## §6. 채택 기능의 WhyMath 형태 — 틀 70·71·74의 최소 착지

갭 리뷰가 **⏸ 승계**로 판정한 72(그룹 학습)·73(토론)은 **재설계하지 않는다** — 정본이 익명 다중 풀이
갤러리·Live Problems로 이미 답했다. 아래는 ⌛·△로 남은 70·71·74뿐이다.

### 70. 교사 클래스 관리 → **기존 코어 상태의 필터링된 투영**

새 계산을 만들지 않는다. L2 엔진(BKT·IRT·합치 진단·약점 추천)은 **이미 초과충족**이고, 없는 것은
계산이 아니라 **역할별 뷰**다. 교사 대시보드 = `access_matrix`로 투영된 학급 집계 + 학생별 ◐ 요약.

- 학급 = D형 컨테이너, 명단 = B형. 학급 집계 = **C형**(개인 재식별 불가 형태로만 산출).
- **미채택 승계**: 출석 관리(매트릭스 #4 "이용 시간대 = 교사 ✕"와 정면 충돌) · 학급 코드 초대 ·
  LMS 연동(`ConsentScope`에 제3자 제공 범위 부재).

### 71. 학부모 → **주 1회 요약 보고서(opt-in)**, 상시 대시보드 아님

§4.3의 ⓒ 좌석. 내용은 `growth_evidence_exposure`의 `GUARDIAN_SUMMARY` 계층 승계 —
**새 지표·새 분류를 만들지 않는다.** 진척·강점 중심, 오답 상세·또래 비교·힌트 사용은 매트릭스상 ✕.

### 74. 과제 배포 → **기존 문항 풀의 학급 배정 + 단계 진단 피드백**

- 과제 정의 = D형(교사 저작·기존 L6 문항 풀 재사용, 신규 저작 파이프라인 0).
- 제출 = A형(학생 답안·시도 로그) + B형(교사 코멘트·채점 결과).
- **자동 채점은 정오 이분법이 아니다** — L5 OCR → L3 PRM 단계검증으로 **"어느 단계에서 막혔는지"**
  를 돌려준다(항목 12). 이는 "정답을 빠르게"를 KPI로 쓰지 않는다는 헌법 금기의 직접 구현이다.
- **미채택 승계**: 성적 반영(이분법 복원) · 예약 배포는 알림 인프라 발화 후.

## §7. 착지 순서 — 뒤집히면 안 되는 체인

```
COLLAB-02 (파기 방향 역전 + 5형 분류 요건)   ← 되돌릴 수 없는 부채이므로 최우선
        ↓
COLLAB-01 (access_matrix.json 계약 + 거버넌스 게이트)
        ↓
[역할 개방 PARENT/TEACHER]  ← 계약이 이미 강제하고 있는 상태에서만
        ↓
COLLAB-03 (일별 집계 writer — 학생 1인칭 좌석에서 선행)
        ↓
협업 스키마 신설 (각 테이블 5형 분류 필수)
        ↓
ⓒ 보호자 링크(Phase 3) → 교사 대시보드 베타(Phase 3) → ⓑ 보호자 계정·B2B 확산(Phase 4)
```

**역전 금지 지점 2개**:
1. **역할 개방이 계약보다 먼저 오면 안 된다** — 개방 순간부터 매트릭스를 사람이 손으로 지키게 된다.
2. **협업 스키마가 파기 규칙보다 먼저 오면 안 된다** — 파기 누락은 사후에 고쳐도 **이미 남은 미성년자
   데이터를 되돌리지 못한다**. 이것이 `COLLAB-02`의 priority가 `COLLAB-01`보다 높은 이유다.
