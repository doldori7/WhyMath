## §1. 방법

판정 규칙 4개를 고정 적용했다.

ⓐ **판정 근거는 실파일 경로·명령 출력·태스크 ID 중 하나여야 한다.** 문서 언급만으로 "충족"한 행은 없다.
ⓑ **trunk 부재 ≠ 미구현.** 다만 이번 세션은 **shallow 클론이라 원격 브랜치 교차 조회를 못 했다**
   (SessionStart 브리핑이 판정 보류를 명시). 따라서 아래 "갭" 판정은 **trunk 기준**이며, 병렬 세션
   인플라이트분이 있을 수 있다 — 이것이 본 대조의 최대 한계다.
ⓒ **식별자 부재 ≠ 기능 부재.** 설계서가 제안한 *이름*으로 0건이면 **역할로 재검색**한 뒤 판정했다
   (예: `canary`가 아니라 "소량 시범 후 임계 미달 시 대량 배치를 차단하는 장치").
ⓓ **부재 주장은 검색 범위를 명시한다.**

```bash
# 재현 — 자산 규모

# 재현 — LLM 생성 배치 vs 결정론 배치
cd src/backend/whymath_backend/harness
grep -l  "router\|llm" *_batch.py | wc -l                       # 1
grep -L  "router\|llm" *_batch.py | wc -l                       # 35

# 재현 — 부재 판정(역할 기반)
grep -rn "canary\|abort_threshold\|fail_rate\|rolling_" src/ scripts/   # 배치 게이트 의미 0건
find . -name "golden*.json"                                     # 0건
grep -rn "import jsonschema" src/ scripts/ tests/               # 0건
```

### A. 골든셋을 "수동 작성"할 것인가 (가장 중요)

| | 설계서 §7 | 저장소 정본 |

| 만드는 법 | **수동 작성 100개** | 검수 이벤트 `verdict`·`failure_code`에서 **승격** (`golden_benchmark_contract.md` §2) |
| 구성 | 정상 60 / 경계 25 / 함정 15 | 앵커 A1~A6 × 30~35 = **180~210건** (`ANCHOR_QUOTA_MIN/MAX`) |

| 인간 시간 | 100건 신규 저작 | **≈ 0** (검수하며 부산물로 생김) |
| 현재 실측 | — | **0건** (`find -name "golden*.json"` 0 · `git log --all` 0) |

계약 §2가 별도 라벨링 캠페인을 금지한 이유는 비용이 아니라 **as-found fail-closed 규약**이다 —
수동 작성 골든은 "QA 엔진이 실제로 본 입력"이 아니므로 승격 경로 자체가 없다. 계약 §8-2의 자인:
*"골든은 검수가 쌓이는 동안에만 싸게 만들어진다. 나중에 만들면 as-found 상태가 복원 불가다."*

**판단이 필요한 지점**: 골든 0건의 원인은 방법론이 아니라 **상류 검수 이벤트가 0건**인 것이다.
설계서 방식으로 100개를 수동 작성하면 골든은 생기지만 **as-found 계약을 깨고**, 그러면
`qa_confusion_matrix`의 FN율 판정 근거가 무효가 된다. → **권고: 미채택**(§8).

## §4. 되돌리기 비싼 제안 4건 — 채택 시 실제 비용

### A. §8 로컬 L2 수치 — 6종 전부 실측과 모순

정본 `docs/ops/amd395_local_llm_performance.md`(786줄 · 2026-08-21~25 Phaiakes9 실측).

| 설계서 | 실측 | 성격 |
|---|---|---|
| Qwen3-30B-A3B **86 t/s** | flash on **71.5 / 72.6 / 72.5** | **+18.5% 과대** |
| GPT-OSS 120B **53 t/s** | **설치 안 됨**(`gpt-oss:20b`만) · 측정 0건 | 문서 등급 **[미측정] = 가정 금지** |
| UMA VRAM **96GB** | **64GB 확정** · 문서가 96GB를 **명시 기각** | 이미 기각된 선택지 |
| **Vulkan** 백엔드 | **ROCm 유지가 확정 조건 #4**(Vulkan은 27b prefill −75.2%·왕복 +68.1%) | 모순 |
| `keep_alive: -1` | `OLLAMA_KEEP_ALIVE=**30m**` · 서버 env 좌석 | 값·좌석 둘 다 불일치 |
| `num_ctx` **4096** | `OLLAMA_CONTEXT_LENGTH=**8192**`(확정 조건 #5) | 불일치 |

**동시 상주 전제가 성립하지 않는다.** 120B(63GB)+30B(18GB)=**약 81GB** vs 카브아웃 **64.4GB**.
문서가 상정한 동시 상주 총합은 **30~35GB**이고, 22GB에서 이미 "커밋 여유 20GB 천장" 선을 그었으며,
Windows ROCm에는 **단일 프로세스 32GB 벽** 보고가 있다(63GB는 그 2배).

> ⚠️ 정본 문서 자신의 측정 규율이 이 인용을 직접 제약한다 — *"프리셋 간 차이가 **20% 미만이면
> 유의하다고 말하지 않는다**"* + 도구 결함 13회차(캐시 히트로 43,542 t/s 허수). **외부 t/s 수치를
> 조건 명시 없이 옮기는 것 자체가 이 문서가 경계하는 실패 유형이다.**

### B. §5 G1·G2·G3을 신설하면 F1~F8 시계열이 오염된다

`eos_verification_design_v1.md` §4가 실패코드 8종을 **폐쇄 동결**했고, 코드 계약은
`schema/enums.py::GenerationFailureCode` + 값집합 동결 테스트다. docstring:

> ⚠️ 폐쇄 8종 — **G0(9/6) 동결 후 12월까지 추가·삭제·의미 변경 금지**
> (검증 중 분류 체계가 바뀌면 실패분포 시계열이 무효가 된다)

설계서 게이트는 이 코드들과 정확히 겹친다:

| 설계서 | 이미 동결된 계약 |
|---|---|
| G1 ② LaTeX 파싱 실패 | **F1** 수식·파싱 실패 (기계) |
| G1 ③ 정답 검산 불일치 | **F2** 정답 불일치 (기계) |
| G2 `level_fit` | **F5** 난이도 미스 (기계+판단) |

| G2 `clarity` | **F7** 언어 수준 부적합 (판단형) |

설계서대로 게이트가 자기 사유 문자열(`errors.append("스키마 위반: …")`)을 만들면
**F-Ⅲ(판단형 F3+F6+F7 합 > 60% = No-Go) 판정의 분모가 오염된다.**
→ **올바른 작업은 "3단 게이트 신설"이 아니라 "게이트 판정 결과를 F1~F8로 강제 분류"다.**
이 경로를 택하면 F1~F8을 손댈 필요가 없어 **G0 동결과 충돌하지 않는다**(타이밍: G0가 **내일 9/6**).

### C. §6 카나리 n=30 + 임계 0.95 — 만족 불가능한 명세

CLAUDE.md 검증 권위 규약: **"게이트 판정은 항상 CLI exit 0/1(Wilson 단측 경계) — 점추정 금지."**
설계서의 `pass_threshold: 0.95` · `min_score: 0.90` · `3% 초과`는 전부 점추정이다.

Wilson 95% 단측 하한(저장소 `harness/wilson.py` 규약):

| 카나리 결과 | 점추정 | Wilson 95% 하한 |
|---|---|---|
| **30/30 (만점)** | 100.0% | **91.7%** ← 95%에 못 미친다 |
| 29/30 | 96.7% | 86.4% |
| 28/30 | 93.3% | 81.7% |

**`size: 30` + `pass_threshold: 0.95`는 만점을 받아도 통과할 수 없다.** 참값 95%를 95% 신뢰로
입증하려면 **전건 통과 n≥60**(60/60 → 95.7%). 선택지는 둘 — **①n을 60으로** 또는 **②임계를 0.90으로**
(30/30 → 91.7% ≥ 90% 통과, 29/30은 탈락).

### D. §6 "본배치 10% 무작위 표본" — 보증 수준이 배치 크기에 따라 30배 흔들린다

결함 0건 관측 시 실제 보증 상한:

| 배치 | 표본(10%) | 결함 0건이어도 상한 |
|---|---|---|
| 300건 | 30 | **8.27%** |
| 1,000건 | 100 | 2.63% |
| 3,000건 | 300 | 0.89% |
| 10,000건 | 1,000 | 0.27% |

저장소는 이미 옳은 방식을 쓴다 — **Wilson min-n**
(`concept_content_review_batch.py::min_n_for_zero_defects`, `n ≥ z²(1−θ)/θ`): **목표 상한에서
필요 표본을 역산**한다.

| 목표 상한 | 필요 표본(결함 0건 기준) |
|---|---|
| F-Ⅱ 2% | **133건** |
| 내용 KPI 0.5% | **539건** |
| 설계서 3% | 88건 |

또한 그 배치는 **결함 주입 표본으로 루브릭 자신의 변별력까지 검증**한다
(CLAUDE.md「보호 장치를 실패 주입 없이 '보호 있음' 선언 금지」) — 설계서에는 이 축이 없다.

> **정정 주의**: 설계서의 "3% 초과 시 전량 격리"를 F-Ⅱ(2%)와 **직접 모순으로 보면 안 된다** — 축이 다르다.
> 저장소에도 3%가 있으나 대상이 다르다: `superhuman_verification_standard.md:134`는
> *"S5 감사 롤링 결함율 3% 초과 시 **게이트 자동 재잠금**"*(배치 격리가 아님).
> 즉 지금 **서로 다른 것을 재는 3% 두 개와 2% 하나**가 공존하며, 필요한 것은 모순 판정이 아니라 **정렬**이다.

## §5. 예시 코드의 결함 (설계서 §5)

예시 코드이므로 결함이 곧 설계 실패는 아니다. **그대로 옮기면 안 되는** 지점만 적는다.

### G-code-1. 검사 4)5)에 인덱스 어긋남 + 거짓 음성

```python
normalized = [str(sympy.simplify(sympy.sympify(c))) for c in choices if _is_math(c)]
if item.get("answer_expr") in normalized[1:]:      # ← 결함 2개
```

`if _is_math(c)` 필터가 리스트를 줄이므로 **`normalized[1:]`는 `choices[1:]`가 아니다**.
그리고 **원시 문자열 `answer_expr`을 정규형 리스트와 비교**한다. 재현(정규화 자리에 분수 정규화 대입):

```
choices    = ['해가 없다', '1/2', '2/4', '3/1']   (길이 4)
normalized = ['1/2', '1/2', '3']                  (길이 3)   ← 인덱스 어긋남
answer_expr='2/4' → '2/4' in normalized[1:] = False          ← 정답이 선지에 있는데 놓친다
```

**거짓 음성이라 조용히 통과한다.** 추가로 검사 3)의 `simplify(lhs-rhs) != 0`은 동치인데 0으로
못 줄이면 **거짓 양성**을 낸다 — 저장소가 3-tier와 도메인 술어 18종을 둔 이유가 이것이다.

### G-code-2. 예외 처리 비대칭 — 검사 2)만 try/except

검사 3)4)5)의 `sympify`가 보호되지 않아 깨진 입력에 **탈락이 아니라 크래시**한다. 설계서 스스로
"예상 탈락률 30~40%"를 말하는데 크래시는 탈락으로 집계되지 않는다 →
CLAUDE.md「측정·수집 도구를 성공 경로만 보고 설계 금지」 정면 위반.

### G-code-3. `sympify`에 신뢰할 수 없는 LLM 출력 투입

`sympify`는 문자열을 평가한다. AI 생성물을 그대로 넣는 것은 알려진 실행 위험 표면이며,
`parse_expr` + 제한된 `local_dict`로 좁혀야 한다.

### G-code-4. G2가 심판에게 정답을 알려 준다 (유도 심문)

```
[의도한 오개념] {misconception}                         ← 알려 주고
1. tag_match: 의도한 오개념을 실제로 유발하는가          ← 그대로 묻는다
```

의도를 알려 준 뒤 "의도대로 됐냐"고 물으면 **tag_match가 부풀려진다**. 블라인드로
*"이 오답지는 어떤 오개념을 유발하는가"* 를 받고 **기계가 대조**해야 한다.
저장소 `cross_verify.py`가 이미 이 원칙을 쓴다 — `_judge_reconstruct`는 LLM에 *재구성*만 시키고
**판정은 기계가** 한다. 또한 `[:400]`·`[:800]` 절단이 **조용하다**(잘린 조각에도 심판은 확신 있는
점수를 낸다) — 절단 사실을 결과에 남겨야 한다. `r.json()["response"]`·`json.loads`·`score[…]`에
예외 처리가 없어 malformed 응답 1건이 배치를 죽인다.

### G-code-5. G3(a)가 SymPy 단일 권위와 충돌할 소지

CLAUDE.md는 SymPy를 동치·검증의 **단일 권위**로 못박았다. 로컬 모델 풀이로 정답을 재판정하면
SymPy가 검증한 건에는 잉여이고, SymPy가 못 푼 건에는 **더 약한 권위로 판정**하게 된다.

| 카나리 임계(§4-C) | **임계를 0.90으로** (n=30 유지) | n=60은 생성·검수 비용 2배이고, 카나리 30건 100% 수동 검수 전제와 겹치면 사람 시간이 두 배로 든다. 1인 개발에서 **사람 검수 시간이 최종 자원**이라는 설계서 §0 전제와 정합 |

| G-4·G-5 | 보류 | 위 §8-ⓒ 사유 |

**임계 0.90의 실제 의미(오해 방지)**: n=30에서 0.90은 관대한 값이 아니라 **사실상 만점 요구**다 —
30/30(하한 91.7%)만 통과하고 **29/30(86.4%)은 탈락**한다. 카나리를 1건이라도 놓치면 본배치가 막힌다.
