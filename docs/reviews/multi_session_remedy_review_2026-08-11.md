## 3. "부적용" 6항목의 공통 근거 — 세션은 tmux가 아니라 컨테이너다

제안은 한 호스트에서 10개 tmux 세션이 도는 그림을 전제한다. 실제로 WhyMath 세션은
**Claude Code 웹(CCR)의 격리된 컨테이너**로 뜨며, 각자 자기 클론을 갖는다(이 검토 세션 =
`/home/user/WhyMath`, worktree 1개, 자체 클론). 호스트를 공유하지 않으므로:

- ⑤ 포트 충돌 · 2차 3(포트 오프셋) — 컨테이너마다 독립 포트 공간. 충돌 불가.
- ⑦ 테스트 DB 오염 · 2차 4(DB 편차) — 컨테이너마다 독립 파일시스템.
- 2차 5(worktree 디스크) — 컨테이너는 세션 종료 시 회수된다.
- 2차 11(Docker 28×10 = 280 컨테이너) — 발생하지 않는다.

**단 Kiki 로컬(Phaiakes9)에서 worktree를 여러 개 열 때는 유효하다.** 그 경우를 위해
`run_demo.sh`에 `WHYMATH_DEMO_PORT`·`WHYMATH_DEMO_DATABASE_URL` 오버라이드가 이미 있고,
`docker-compose.*.yml`이 포트를 수동으로 분리해 둔다(5433 prod · 5434 pilot · 55432 demo).
세션 번호 기반 자동 할당은 없으나, 로컬 동시 worktree가 실제로 문제가 된 사례가 아직
관측되지 않았으므로 등재하지 않는다.

## 4. 개별 심화 판정

### ④ 스키마 계약 — 관례만 있다 (부분·이번 범위 밖)

`db/schema_version.py`가 7개 브랜치에서 동시 수정 중이다. 전례도 있다: 2026-07-30
`shadow-data-s3-pilot-nh5kbz` 9일 고립 때 SEC-01이 main과 shadow 양쪽에서 각자 alembic을
생성해 **리비전 ID `d5e6f0a1b2c3`이 동시 채번**됐다. Kiki가 제안한 "마이그레이션 파일
버전 넘버링으로 순서 보장"은 정확한 처방이지만, 이 저장소에는 그 순서를 **기계로 검사하는
장치가 없다**. 등재 후보이나 이번 검토 범위 밖으로 둔다.

### ⑥ TASK_BOARD.md 락 — 채택 금지

Kiki가 2차 리스크 2에서 스스로 지적한 "락 시스템이 락 대상이 되는" 문제가 정확하다.
이 저장소는 이미 그 단계를 지났다:

- **현행**: `harness-claims` 브랜치에 태스크당 JSON 1개, `git push --force-with-lease`의
  **CAS 원자성**으로 동시 `start` 시 정확히 한쪽만 성공한다. 트리는 `git mktree`로 만들어
  인덱스를 안 쓰므로 개발자 스테이징 오염이 구조적으로 불가능하다.
- **제안된 Redis `SETNX`도 여기선 후퇴다** — CCR 컨테이너 간에 도달 가능한 공유 Redis가
  없다. git 원격은 이미 모든 세션이 공유하는 유일한 조율 매체다.

### ⑫ 오케스트레이터 — 직관은 맞다. 단 그것은 세션이 아니라 CI여야 한다

2차 리스크 1(SPOF)·12(관찰 지연)·요약리스크 1(관측성)은 뿌리가 같다. Kiki의 처방인
"세션 하나를 통합 담당으로 고정"은 **이 환경에서 구조적으로 불가능하다**:

- 세션 컨테이너는 **전부 shallow 클론**이라 트렁크 히스토리 기반 판정을 할 수 없다(F3).
- 세션은 수명이 짧고 원격 브랜치를 스스로 삭제하지 못한다(HARN-16 — 403).

오케스트레이터 역할의 정당한 거처는 **CI 러너**다. full clone이 공짜이고, 상시 존재하며,
저장소 토큰으로 쓰기가 가능하다(`branch-cleanup.yml`이 이미 실증). `HARN-27`·`HARN-28`이
이 방향이다.

### 2차 9 — AI 합의 오류 증폭 (미채택)

"10개 세션이 다 Claude면 같은 편향을 공유한다"는 지적은 타당하나, 현재 이 저장소의 실제
손실은 편향이 아니라 착지 실패에서 나온다(최근 60커밋 중 11건). 우선순위상 등재하지 않는다.

### 2차 2 — ID 번호 충돌은 여전히 미해결 (기등재)

번호 가드는 존재하지만 **관측만 하고 예약하지 않는** TOCTOU가 남아 있다. 2026-08-11
두 세션에 같은 빈 번호(OPS-29)를 동시 제안해 실충돌이 났다. `HARN-22` **todo**.
이 검토 세션도 `add` 시 HARN-25가 미머지 브랜치에 이미 있다는 이유로 거부당했다 —
가드가 작동했고, 제안된 번호(HARN-26)를 그대로 썼다.

## 5. 진짜 갭 3건 — 기등재 태스크로 덮이지 않는다

### F1 → `HARN-26` (완료) — 고아 claim이 실작업을 차단 중이었다

이 세션 브리핑의 "착수 금지" claim 5건 중 **3건**이 origin에 존재하지 않는 브랜치를
홀더로 지목했다(MATH-01·MATH-02·HARN-20). `stale_claims()`의 판정 기준 3종
(`ttl`·`task_done`·`task_missing`)에 **홀더 브랜치 부재 축이 없었다.**

> **자기정정 (중요)**: 40분 뒤 재측정에서 MATH-01·MATH-02의 브랜치는 **존재했다**
> (원격 브랜치 44→47). 두 세션은 죽은 게 아니라 `start`와 첫 push 사이의 정상 구간에
> 있었다. **실제 고아는 5건 중 1건**(HARN-20 — 홀더 브랜치 소멸 + main에서 이미 `done`)
> 뿐이었다. 이 관측이 유예(`claim_branch_grace_hours`)를 이론이 아니라 필수 방어로
> 만든다 — 유예 없이 집행했다면 살아 있는 세션 2건의 claim을 지워 CAS가 막아둔 중복
> 착수를 직접 열어줬을 것이다.

유예 24시간의 근거(`backlog/events.ndjson` start→done/block 199건):

```
p50 0.46h · p75 0.89h · p90 1.50h · p95 5.15h · p99 54.0h · max 66.4h
4h 초과 10건(5.0%) · 24h 초과 4건(2.0%) · 72h 초과 0건(0.0%)
```

**TTL(72h) 재사용은 변별력이 0이다** — 72h를 넘긴 세션이 하나도 없으므로 `branch_gone`이
잡는 집합이 `ttl`의 부분집합이 된다.

### F2 → `HARN-27` (완료) — reap의 집행 지점이 없었다

`claims reap --apply`는 **CLI에 존재했다**. 그것을 부르는 자동 경로가 없었을 뿐이다.
`ci.yml:1017`은 dry-run만 돌리고 1026행에서 *"`--apply`로 청소 권장"* 이라는 경고를 냈다 —
**아무도 실행하지 않는 명령을 권하는 상태**였고, 그래서 HARN-20(main에서 이미 `done`,
기존 `task_done` 기준에 이미 해당)의 claim이 영구히 남았다.

CLAUDE.md 위반 2건: *"정본화를 집행으로 착각한 완료 선언 금지"* · *"상시 실패하는
fail-open 보호를 '보호 있음'으로 신뢰 금지"*.

집행 지점 = `.github/workflows/harness-audit.yml`. 자동 청소는 **확정 사유
(`task_done`·`branch_gone`)에 한정**하며, 그 집합은 YAML이 아니라 파이썬 상수가 소유한다.

### F3 → `HARN-28` (미착수) — 고립 탐지기가 실행 환경에서 구조적으로 꺼져 있다

`scan_stale_branches()`는 shallow 클론이면 `status="shallow"`로 판정을 포기한다
(`remote_claims.py:1252`). **모든 CCR 세션 컨테이너가 shallow 클론**이다 — 이 세션
브리핑도 "판정 보류"를 냈다. HARN-13 탐지기는 모든 세션이 사는 환경에서 **한 번도
실행된 적이 없다.**

2026-08-11 세션이 `unmerged_branch_verdict_2026-08-11.md` §1에서 이 상태를 예언했다:

> *"모든 세션 컨테이너가 shallow라면 이 스캐너는 다시는 목록을 내지 않는다. 그 경우 이
> 수정은 문제를 해결한 게 아니라 침묵을 정직한 침묵으로 바꾼 것이다."*

같은 문서가 `--unshallow` 자동 실행을 기각했고(훅이 매 세션 도는 경로 · stderr 폐기 ·
컨테이너가 매번 새로 생성), **그 기각은 타당하다**. 따라서 `HARN-28`의 방향은 기각을
뒤집는 것이 아니라 **스캔의 실행 위치를 세션 밖(CI 러너·full clone)으로 옮기는 것**이다.

이 미측정 상태가 가리는 규모 = §1-2의 수치(미머지 커밋 392 · PR 없는 브랜치 27 · 최장 8일).

## 6. 정직한 공백

- **§1-2의 27건·392커밋은 "폐기 대상"이 아니라 "판정되지 않은 상태"다.** 개별 브랜치의
  회수/폐기 판정은 이 문서 범위 밖이며, 2026-08-04·08-11 판정 문서가 그 작업의 선례다.
- **④ 스키마 계약과 2차 9(모델 다양성)는 등재하지 않았다.** 실피해가 관측된 항목만
  등재하는 이 저장소 관례를 따랐다 — 필요하면 별도 판단으로 등재한다.
- **`HARN-28`은 이 세션에서 구현하지 않았다.** 등재만 된 상태이며, 실행되지 않으면
  고립은 그대로다(2026-08-11 판정 문서 §3과 같은 종류의 공백).
- **`HARN-27`의 CI 배선은 이 문서 작성 시점에 실제 러너 실행으로 실증되지 않았다.**
  PR·머지 후 런 로그로 확인해야 완결된다 — "저장소에 존재함"과 "돌아감"은 다르다.
