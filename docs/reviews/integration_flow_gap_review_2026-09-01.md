## 0. 요약 — 진단이 뒤집힌 지점

일반론(“PR이 쌓여 정체된다”)을 이 저장소에 그대로 적용하면 **틀린 처방**이 나온다.
실측 결과 이 저장소의 병목은 PR *체류*가 아니라 PR **미생성**이다.

| 축 | 실측값 | 판정 |
|---|---|---|
| PR 생성→머지 중앙값 | **1.1시간** (n=180) | 🟢 병목 아님 |
| 24시간 내 머지 비율 | **89%** | 🟢 병목 아님 |
| 72시간 초과 PR | 180건 중 4건 | 🟢 병목 아님 |
| main CI 최근 30회 | success 23 · cancelled 7 · **failure 0** | 🟢 병목 아님 |
| 저장소 위생 (`git status`) | **0건** · 추적 아티팩트 0건 | 🟢 병목 아님 |
| PR 없이 방치된 브랜치 | **18건** (최대 29일) | 🔴 **병목** |
| trunk 대비 표류 | **18건이 50커밋+ 뒤처짐** (최대 248) | 🔴 **병목** |
| main과 이미 충돌 중인 브랜치 | **32건 중 24건** | 🔴 **병목** |
| 열린 PR 중 충돌 상태 | **14건 중 8건** | 🔴 **병목** |

**결론**: 파이프라인은 건강하다. 문제는 파이프라인에 **들어가지 않은 작업**이다.
따라서 “리뷰를 빨리 하자 / CI를 빠르게 하자”는 이 저장소에서 효과가 거의 없다.
효과가 있는 것은 **PR 미생성 상태를 가시화하고 만료시키는 것**이다.

사용자가 제시한 우선순위(①Branch Drift ②Stale PR ③PR Dependency ④CI/Review Delay
⑤Excessive WIP) 중 **②와 ④는 이 저장소에서 이미 해결된 상태**이므로, 자원을
①③⑤에 집중하는 것이 옳다.

## 2. 종합대책 — 4계층

방해요인은 개별 이벤트가 아니라 **연쇄**로 위험해진다. 따라서 대책도 연쇄를
끊는 지점에 배치한다.

```
장기 브랜치 → 표류 → 큰 PR → 리뷰 지연 → CI 실패 → 충돌 → PR 장기화 → PR Stack
     ↑                                                          ↑
   [L1] 가시화                                              [L4] 만료
```

### L1. 가시화 — 재지 않으면 존재하지 않는다
표류·충돌·겹침·WIP를 **매일 자동 측정**한다. 이 저장소의 실패는 대부분
“아무도 몰랐다”이지 “알고도 안 했다”가 아니다. → **적용함** (§3)

### L2. 조기 통합 — 충돌 비용은 시간에 단조 증가
충돌 24건은 하루아침에 생기지 않았다. 표류가 임계를 넘기 전에 trunk를 브랜치로
당겨온다. 규칙: **50커밋 / 14일** 중 먼저 오는 쪽. → 측정은 적용, 집행은 사람 판단

### L3. 소유권 분리 — 겹침은 사후 충돌이 아니라 사전 배분 문제
PR-04 실측(3 PR이 21~32파일 공유)은 이미 `pathscope`·claim 대장이 있는데도
발생했다. 원인은 **claim이 태스크 단위인데 브랜치는 그보다 오래 살기 때문**이다.
→ 겹침 측정을 적용, 배분 정책은 §5 후속 태스크

### L4. 만료 — 결정하지 않는 것도 결정이다
PR 없는 18건은 “나중에 판단”이 21일 누적된 결과다. CLAUDE.md는 이미
**“만료 없는 유예·제외 금지”**를 금기로 등재했다 — 그 원칙을 브랜치에 적용한다.
→ 측정·경보를 적용, 삭제 배치는 기존 `/stray-code`가 담당

## 3. 적용 — `scripts/ops/flow_health.py`

### 3.1 무엇을 만들었나
빈 축 5개(GIT-01·GIT-04·PR-03·PR-04·FLOW-01)만 채우는 측정기.
**겹치는 축은 재구현하지 않았다** — `backlog.py branches`의 소유자 판정,
`pr_delivery_audit`의 배송 판정은 그대로 두고 호출만 배선했다.

### 3.2 설계 계약 (CLAUDE.md 준수)

| 원칙 | 구현 |
|---|---|
| 측정 실패 ≠ 통과 | shallow·git 오류 → **exit 2**. `--warn-only`도 이것은 낮추지 않는다 |
| 침묵 실패 금지 | 모든 실패 사유에 **예외 타입명** 포함 |
| 실패해도 증거가 남는다 | `--jsonl` 브랜치 1건마다 즉시 flush |
| 모든 외부 프로세스에 타임아웃 | git 60s · curl 30/40s · 페이징 상한 5 |
| 판정은 exit code | 0=신호없음 · 1=신호있음 · 2=측정불가 |
| 외부 인프라 의존 금지 | 핵심 판정은 **순수 git**. API 실패해도 표류·충돌은 측정됨 |
| 로케일 인코딩 금지 (HARN-19) | 전 subprocess `encoding="utf-8"` 명시 |

### 3.3 개발 중 발견해 고친 결함 2건 (기록)

**① `refs/pull/<N>/head` = “제출된 적 있음”이지 “열려 있음”이 아니다**
초기 구현은 PR ref 존재만으로 “PR 있음”을 판정했다. 실측하니 **PR #675는
closed·unmerged인데 브랜치 tip과 일치**해서, ⓐ리뷰 부하가 없는 PR에 PR-03이
발화하고 ⓑ트렁크 밖에 남은 작업이 WIP 집계에서 빠졌다. → `pr_ref`(제출 이력)와
`pr_open`(현재 열림)을 **분리**하고, 열림 여부를 모르면(`None`) PR-03은
**발화하지 않는다**(추측으로 신호를 만들지 않는다). 이 회귀는 테스트로 동결했다.

**② 로케일 인코딩 디코드 3건** — 저장소의 기존 거버넌스 테스트
`test_subprocess_encoding.py`(HARN-19)가 잡았다. Kiki 머신(한국어 Windows·cp949)
에서 한글 브랜치명·커밋 제목을 디코드할 때 붕괴하는 코드였다.
**기존 방어 장치가 신규 코드에 대해 실제로 작동함을 확인한 사례다.**

### 3.3b 리뷰에서 잡힌 결함 4건 (Codex P2 · 전건 수용)

기계 리뷰가 P2 4건을 냈고 **전부 실측으로 확인돼 수정**했다. 네 건 모두
**이 문서가 세운 원칙을 코드 자신이 위반한** 형태였다는 점이 공통적이다.

| # | 결함 | 실측 확인 | 위반한 자기 원칙 |
|---|---|---|---|
| 463 | `_active_branches`가 존재하지 않는 `load_remote_claim_map`을 부르고, `sys.path`도 틀려(`scripts` → `scripts/harness`) 두 예외를 광범위 `except`가 **삼켰다** | claim 3건이 살아 있는데 `frozenset()` 반환 → 타 세션 작업 브랜치 3개가 dormant로 오분류 | **침묵 실패 금지** |

가장 뼈아픈 것은 463이다. 이 도구의 docstring이 "침묵 실패 금지"를 명시하는데
정작 `_active_branches`의 `except Exception`이 **오타 두 개를 무증상으로 삼키고**
있었다. 그래서 실패 사유를 반환값 `(집합, 사유)`으로 올려 리포트에 남기도록 고쳤다.
회귀는 뮤테이션 5종으로 동결했다(전건 검출).

### 3.4 배선 (정본화 ≠ 집행)

`harness-audit.yml`에 `flow-health` 잡 추가 — 야간 schedule + main push + dispatch.

- `fetch-depth: 0` — 없으면 ahead/behind가 **틀린 수**가 된다
- `--warn-only` — 남의 방치 브랜치로 무관한 PR을 red로 만들지 않는다(관측 잡)
- `contents: read` — claim-reap의 쓰기 권한이 관측 잡으로 새지 않도록 격리
- **고아 도구 `pr_delivery_audit.py`를 같은 잡에서 호출** — 호출처 0건 상태 해소
- 측정 원본을 artifact로 30일 보존
