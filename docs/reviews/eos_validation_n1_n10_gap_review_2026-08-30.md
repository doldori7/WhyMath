## §0. 결론 요약

외부 문서의 핵심 주장 — *"382개 기능 목록에는 검증 구조를 지탱할 항목이 하나도 없다"* — 은
**우리 저장소에는 성립하지 않는다**. 제안 10건 중 **4건은 이미 착지**했고(그중 1건은 원격
미머지), **4건은 부분 착지**, **2건만이 실제 신규**다. 다만 그 2건이 하필 **EOS 검증설계서
§6 내용 KPI 6종 중 4종의 측정 근거**여서, 규모는 작지만 차단력은 크다.

| 판정 | 건수 | 항목 |
|---|---|---|
| **이미 구현** | 4 | N3(#909 머지) · **N5**(#912 머지 — 잔여 3축) · N7 · N9 |
| **부분**(갭 명시) | 4 | N1 · N2 · N4 · N6 |
| **신규**(진짜 빠짐) | 2 | **N8 골든 벤치마크** · **N10 실험 레지스트리** |
| 제안 중 **미채택 권고** | 2 | N2의 관계타입 7종 신설 · N1의 별도 Validation 스키마 신설 |

**가장 중요한 발견 3가지**

1. **N8 부재 = EOS-51 §6 내용 KPI의 집행 공백.** 설계서는 "오개념 op-code 라벨 정확도 ≥85%",
   "교육과정 정합률 ≥92%(블라인드 역매핑)", "풀이 비약 지적률 ≤10%(**LLM 심판 κ≥0.5일 때만
   전수 확장**)"을 목표로 동결했다. 그런데 κ(심판↔인간 일치도)를 계산하려면 **인간 라벨 정답지**가
   있어야 한다. 저장소 전수 검색 결과 그런 데이터셋도, 그것을 만드는 태스크도 **0건**이다.
   즉 *지표는 동결됐는데 지표를 계산할 재료가 백로그에 없다*. 이것이 이번 검토의 최대 수확이다.
2. **N3은 "없는 것"이 아니라 "미머지"였다.** 초판 대조 시점에 trunk `hit_cu_metrics` grep
   0건이었으나 원격에 **2,379줄·테스트 82건으로 done** 상태였고, 같은 날 **#909로 머지**됐다.
   CLAUDE.md "trunk 부재를 미구현으로 단정 금지" 규칙이 그대로 발동한 사례다 — ①코드 grep만
   했으면 "신규"로 오판해 **이미 있는 계측기를 다시 만들 뻔했다**.
3. **N7(Acceptance Gate)은 외부 문서보다 우리가 앞서 있다.** 문서 §24가 경고한 "11월에 목표를
   낮춰 PASS시키는" 시나리오는 EOS-51 §5가 이미 *"F-Ⅰ~F-Ⅴ는 G0 서명 후 12월까지 수정 금지"*로
   명문 봉인했고, 문서 §38이 권고한 "단일 점수 금지 → Hard Gate + Score"도 F-Ⅰ~Ⅴ(하드 게이트) +
   판정 3단계(Go/Conditional/No-Go) 구조로 이미 채택돼 있다.

## §1. 검토 방법 (판정 절차)

CLAUDE.md **"trunk 부재를 '미구현'으로 단정 금지"** 규칙을 절차로 집행했다.

| 단계 | 수단 | 목적 |
|---|---|---|
| ① 코드 실측 | `grep -rn` (src/·scripts/·tests/) | 좌석 실재 확인 |
| ② 백로그 실측 | `backlog/tasks/` 449건 전수 | 등재된 계획 확인 |
| ③ **원격 실측** | `git log --all --grep=EOS-5` · `git branch -r` | **미머지 완료분 확인** |
| ④ 게이트 실측 | `backlog/gates.yaml` | 사람 게이트 대기 여부 |

③이 실제로 판정을 뒤집었다(N3). ①만 했으면 "미구현" 오판이 났을 항목이다.

**판정 4분류**: `이미 구현`(파일 경로 증거 필수) / `부분`(갭 축 명시) / `신규`(전수 0건) /

## §3. 항목별 상세

### 3.1 N1 — 앵커: 설계는 앞섰고 등록만 남았다

문서는 앵커 8개(A1 분수 ~ A8 선형대수)를 권고했다. 우리는 **6개로 이미 확정**했고, 그 축소는
임의가 아니라 실사 근거가 있다.

| | 외부 문서 제안 | 우리 확정(EOS-51 §1-1) |
|---|---|---|
| 개수 | 8개(초3~대학) | **6개** — A7(ε-δ)·A8(선형대수) **2027-01 이월** |
| 근거 | "6~8개가 적당" | EOS-52 실사: A7·A8은 성취기준·원자는 기적재이나 **오개념·문항·기계판정 채널이 전부 0** |
| 잃는 것 | — | "대학 범위 자동검증 한계선의 12월 확인"(명시적 손실로 문서화) |
| 깊이 앵커 | A1 초3 분수 | **A4 중3 이차방정식** (기존 문항 378·오개념 8·op-code 3 — 자산이 가장 두꺼운 단원) |

> **문서와의 차이가 의미 있는 지점**: 문서는 깊이 앵커를 *가장 쉬운* 초3 분수로 잡았다. 우리는
> *자산이 가장 많은* 중3 이차방정식으로 잡았다. 문서 §4.1이 경고한 "작업하기 쉬운 단원만
> 반복 테스트" 함정을 피하려면 깊이 앵커는 쉬움이 아니라 **폐쇄루프 완주 가능성**으로 골라야
> 하며, A1은 실사 결과 **기존 문항 0건**이라 깊이 앵커로 두면 12월까지 루프를 못 닫는다.

**잔여 갭**: 앵커가 `ANCHOR_DEFS` 파이썬 상수로만 존재한다. 생산 배치·계측 CLI가 앵커 축으로
조인하려면 1급 등록이 필요하다(`EOS-56`). 단 **문서 §7의 `validation_anchor` 테이블 신설안은
그대로 채택하지 않는다** — §4-② 참조.

### 3.2 N2 — 수직 연결: 필요하지만 제안 형태로는 위험하다

문서 §9는 관계타입 7종 신설을 권고한다:
`PREREQUISITE_OF` / `GENERALIZES_TO` / `SPECIAL_CASE_OF` / `REPRESENTATION_EVOLVES_TO` /
`PROCEDURE_EXTENDS_TO` / `DEFINITION_REFINED_AS` / `ABSTRACTION_OF`.

**이 제안은 반려한다**(§4-① 상세). 대신 문서 §10이 제기한 *진짜 질문* — "학생이 중2 일차함수에서
막혔을 때 어떤 초등 개념까지 거슬러 올라가는가" — 은 우리 실측에서 **정확히 실패하고 있다**:

```
전체 PREREQUISITE 엣지        2,210
학교급 경계를 넘는 엣지           20  (0.9%)
고등 → 대학 경계 엣지              0  ← 역추적이 학교급 벽에서 끊긴다
```

즉 **엣지 타입이 부족한 게 아니라 엣지 자체가 없다.** 타입을 7종으로 늘려도 초→중 연결이 20개면
수직 연결은 여전히 성립하지 않는다. 조치는 타입 신설이 아니라 **`CUR-06`의 우선순위 상향**이다
(현재 stage S4 · priority 3 → EOS-51 §2가 "학교급당 2개" 원칙으로 앵커를 짠 이상, 경계 엣지는
G3(11/22 폭 확장) 전에 필요).

문서 §52도 "N2는 규모를 줄여도 **대표 Vertical Chain 하나는 반드시** 실제 그래프 데이터로
만들라"고 했다. 이 축소안이 우리 상황에 정확히 맞는다 — 앵커 6개를 관통하는 체인
(`분수 A1 → 비와 비율 A2 → 이차방정식 A4 → 이차함수 A5 → 도함수 A6`) 1줄이면 충분하다.

| **판정 5종** | `verdict ∈ {approved, rejected}` 2값뿐 | ❌ |

**판정 해상도 갭이 실질적으로 문제인 이유**:

```
현재:  approved  ──┬── 그대로 통과한 CU
                   └── 사람이 5분 고쳐서 통과시킨 CU     ← 구분 불가

결과:  HIT 중앙값 4분 달성 + 승인율 93%  →  "성공"으로 보이지만
       실제로는 승인분의 40%가 손질된 것일 수 있고, 그 40%는
       AI-first 전략의 실패 신호다 (문서 §14의 "실질 생산시간" 논지)
```

문서 §17이 제안한 5종(`APPROVED` / `APPROVED_WITH_EDIT` / `REGENERATE` / `REJECTED` / `ESCALATE`)
중 **`APPROVED_WITH_EDIT` 1종만 추가하면** 이 구멍이 닫힌다. `REGENERATE`는 Run 로그(N5)가,
`ESCALATE`는 운영 절차가 담당하므로 스키마 확장은 최소로 둔다.

### 3.7 N8 — 이번 검토의 최대 발견

**전수 0건**이다. 그런데 EOS-51 §6이 동결한 내용 KPI 6종을 뜯어보면 4종이 골든 라벨에 의존한다:

| 내용 KPI (동결 목표) | 측정에 필요한 것 | 현재 |
|---|---|---|
| 수학적 오류율 ≤0.5% | SymPy 전수 ✅ + **독립 모델 심판 전수** + 층화 인간 검수 | 심판 정확도 미검증 |
| 교육과정 정합률 ≥92% | **블라인드 역매핑 정답지**(앵커당 20 CU) | 없음 |
| 오개념 op-code 라벨 정확도 ≥85% | **인간 라벨 정답지** | 없음 |
| 풀이 비약 지적률 ≤10% | 3점 루브릭 + **LLM 심판 κ≥0.5 확인 후에만 전수 확장** | **κ 계산 불가** |

문서 §26이 지적한 대로, 교육 콘텐츠에서 결정적인 것은 **False Negative(틀린 콘텐츠를 정상이라
판정)** 인데, 우리 QA 엔진은 **자기 FN율을 모른다**. `qa_pipeline.py`가 9축을 조립해 PASS/FAIL을
내지만, 그 PASS가 얼마나 믿을 만한지 측정한 적이 없다.

```
현재:   생성 → QA 엔진 → PASS  →  (그대로 신뢰)
필요:   골든 200건(전문가 라벨) → QA 엔진 → 혼동행렬
                                         ├─ Precision
                                         ├─ Recall
                                         └─ FN율  ← 무관용 관리 대상
```

**규모**: 문서 §25는 문제 1,000 + 풀이 1,000 + 오개념 300 + 힌트 500 + 학생응답 500을 제안하지만,
우리 12월 일정(검수 예산 185 CU)에는 과대하다. **앵커 6개 × 30~35건 ≈ 200건**이면 §7-3이 인정한
검출력 한계 안에서 FN율의 자릿수는 잡힌다. 그리고 이 200건은 **새로 만드는 게 아니라
EOS-54 검수 이벤트에서 자동으로 쌓인다** — 검수 판정 자체가 라벨이다. 필요한 것은
"검수 결과 중 골든으로 승격할 표본을 고르고 동결하는 규약"이지, 별도 대량 라벨링 캠페인이 아니다.

### 3.8 N10 — 실험 레지스트리

`experiment_id` 전수 0건. 현재 우리 개선 사이클은 이렇게 돌아간다:

```
프롬프트 수정 → 배치 재실행 → 결과가 좋아 보임 → 채택
                                    ↑
                        무엇과 비교했는지, 표본이 몇이었는지,
                        같은 조건이었는지가 어디에도 없다
```

문서 §30의 Experiment 레코드(가설·변형군·표본수·지표)가 있으면 이것이
`Experiment → Evidence → Decision`으로 바뀐다. 다만 **12월 필수는 아니다** — 문서 §52도 축소
가능으로 분류했다. 실제로 우리에게 시급한 것은 실험 *레지스트리*보다 §3.5의 **Run 마디**이며,
Run에 `experiment_id` 널 컬럼 하나만 미리 두면 12월 이후 확장 비용이 0에 가깝다.

## §4. 제안 중 **채택하지 않을 것** (아키텍처 충돌)

검토 요청의 절반은 "무엇을 더 만들까"지만, 나머지 절반은 **"무엇을 만들지 않을까"** 다.

### ① N2의 관계타입 7종 신설 — **반려**

CLAUDE.md 8대 구조 원칙 #3(**Relation Typing 최소화 — 5~8개 핵심 관계만**)과 7대 붕괴 연쇄의
2단계(**관계 폭발 → 순환참조 → 유지보수 지옥**)에 정면으로 걸린다.

| | 현재 | 문서 제안 적용 시 |
|---|---|---|
| 관계타입 수 | 6종(`PREREQUISITE`·`COMPOSED_OF`·`ANALOGOUS_TO`·`EXTENDS`·`CONTRASTS`·`TRIGGERS_DISTRACTOR`) | **13종** (상한 8 초과) |
| DAG 강제 | `PREREQUISITE`만 | 신설 7종의 순환 판정 규약 전무 |
| 의미 중복 | — | `GENERALIZES_TO` ≈ 기존 `EXTENDS`("A를 일반화하면 B") · `ABSTRACTION_OF`는 그 역방향 |

게다가 §3.2에서 봤듯 **진짜 병목은 타입이 아니라 엣지 수(경계 통과 0.9%)** 다. 타입을 늘리면
"이 관계가 없으면 AI 튜터링에서 실제 어떤 오류가 나는가"라는 관계 추가 하드 게이트를 통과하지
못하는 약한 엣지만 늘어난다.

**대안**: 기존 `EXTENDS`를 학교급 경계에서 재사용하고, 필요하면 엣지 **속성**(`crosses_school_level`
같은 플래그)으로 처리한다 — 타입 축이 아니라 속성 축.

### ② N1·N10의 별도 Validation 스키마 신설 — **축소 채택**

문서 §45는 `validation_anchor` / `generation_run` / `human_review` 3테이블 신설을 권고한다.
우리는 EOS-51 §3에서 CU에 대해 **"기존 스키마 조합으로 표현한다 — 신설 스키마 금지(이중 진실
원천·과공학 방지)"** 를 이미 동결했고, 같은 판단이 여기에도 적용된다.

| 문서 제안 테이블 | 우리 처리 |
|---|---|
| `validation_anchor` | **YAML=소스 · DB=산출물** 단방향(EOS-56 ①) — 신설 테이블 아님 |
| `human_review` | **`review_timer_event`가 이미 그 역할**(append-only·판정·failure_code) — 중복 신설 금지 |
| `generation_run` | **유일하게 정당한 신설** — 현 `GenerationLog`가 호출 단위라 묶음 마디가 실제로 비어 있음(§3.5) |

### ③ N9의 5대분류 재편 — **미채택**

문서 §27의 `CONTENT/PEDAGOGY/CURRICULUM/FORMAL/AI` 5대분류는 F1~F8보다 표현력이 높지만,
**F1~F8은 이미 G0 동결 대상**이며 F-Ⅲ 판정("판단형 F3+F6+F7 합 > 60% = 실패")이 이 8코드 위에서만
성립한다. 12월 중 분류 체계를 바꾸면 실패분포 시계열이 무효가 된다.

단 문서가 짚은 **`HALLUCINATION`·`FORMAT_FAILURE`·`NON_DETERMINISTIC_FAILURE`** 는 F1~F8에
직대응이 없다. 이들은 *콘텐츠의 결함*이 아니라 *생성기의 결함*이라 축이 다르다 —
**반려코드가 아니라 Run 로그의 `error_detail`/실패 원인 축**에서 다루는 것이 옳다(N5 확장 시 반영).

## §8. 한계 (정직)

1. **원격 브랜치 전수 확인은 못 했다.** 세션 브리핑이 shallow 클론으로 인해 장기 미머지 브랜치
   판정을 보류했다(`git fetch --unshallow` 필요). N8·N10이 어느 미머지 브랜치에 존재할
   가능성은 `git log --all --grep`으로 EOS 계열만 확인했으므로 **완전 배제되지 않았다.**
   등재 전 `backlog.py add`의 번호 충돌 검사(로컬+원격 claim 대장)가 2차 방어선이다.
   **이 한계는 실제로 발현했다** — 등재 시점에 `EOS-60~63`이 이미 원격 선점 상태여서 CLI가
   번호를 재배정했고(`EOS-64` notes), 초판이 "todo"로 적은 3건이 그 사이 done이 됐다(§9).
   즉 이 저장소에서 **"현황"은 한 세션 길이보다 짧게 유효하다.**
2. **prod DB는 조회하지 않았다.** 본 검토의 "0건" 판정은 전부 저장소 실측이며, prod
   `whymath-pg:5433`에만 존재하는 데이터는 보지 못했다. 다만 N8·N10은 *스키마·코드*가 없으므로
   DB에 데이터만 있을 가능성은 구조적으로 낮다.
3. **외부 문서의 원본 xlsx(382개 기능 목록)는 저장소 밖이다.** 본 검토가 대조한 것은 docx에
   전사된 41행 요약이므로, 382건 전체와의 대조는 아니다. 그 축의 전수 대조는 `EOS-53`
   (53행·부록 A 기준)이 이미 수행했고 본 문서는 그 위에 N1~N10만 겹쳤다.
4. **KPI 목표값의 타당성은 검토 대상이 아니었다.** EOS-51 §7-1이 스스로 "실측 벤치마크가 아니라
   산술 손익분기 도출값"이라 명기했고, G2(10/25) 재조정이 정상 경로로 규정돼 있다.

### 9-c. 이름 충돌 주의 — `EOS-64`와 `EOS-60`은 다른 축이다

같은 날 등재된 `EOS-64-anchor-e2e-nightly-golden`이 "골든"이라는 같은 단어를 쓴다. **중복이

| | `EOS-64` (골든 **승격 경로**) | `EOS-60` (골든 **벤치마크 셋**) |
|---|---|---|
| 묻는 질문 | 이 콘텐츠를 출시해도 되는가? | **우리 QA 엔진이 얼마나 맞히는가?** |

| 산출 | review_status 백필 · Wilson 게이트 통과 | **혼동행렬 · Precision/Recall/FN율** |
| 방향 | 콘텐츠를 판정한다 | **판정기를 판정한다** |

`EOS-64`가 아무리 잘 돌아도 QA 엔진의 FN율은 여전히 미지수다 — 승격 경로는 판정기를 믿고

(별도 라벨링 캠페인 금지 — `EOS-60` acceptance ①). 의존 방향은 `EOS-64` → `EOS-60`이다.
