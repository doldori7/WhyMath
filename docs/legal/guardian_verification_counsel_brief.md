## 1. 서비스 요약 (변호사용 1쪽)

**무엇을 하는 서비스인가.** WhyMath(와이매스)는 한국 중·고등학생 대상 AI 수학 학습 앱이다. 학생이 문제를 풀다 막히면 정답을 바로 주는 대신 단계별 힌트·질문으로 사고를 이끄는 코칭형 서비스이며, 손글씨 풀이 사진 인식·개념 진단·학습 경로 추천을 제공한다. 태블릿 앱(카카오/네이버 소셜 로그인)으로 이용한다.

**어떤 개인정보를 다루나 (실측).** 수집 항목과 저장 상태는 다음과 같다(정본: `docs/architecture/db_backup_dr_runbook.md` §4의 ORM 실측 표, 166~172행):

| 항목 | 저장 상태 |
|---|---|
| 이메일 (카카오/네이버 로그인 식별자) | **원문 미저장** — sha256 해시(64자)만 저장¹ |
| 출생 연도(birth_year) — 연도만, 월일 미수집 | 평문² |
| 닉네임·성별·학교 지역/유형·학년·목표 대학 등 프로필 | 평문² |
| 학생-AI 대화 내용·손글씨 풀이 이미지 | **앱 계층 암호화**(AES-256-GCM 봉투 암호화 — 도입 이전의 과거 행은 평문 잔존 가능)³ |
| 풀이 시도·평가 등 학습 활동 기록 | 평문³ |
| 실명·전화번호·주소 | **수집하지 않음** (데이터 최소 수집 원칙)⁴ |

¹ `src/backend/whymath_backend/api/auth.py:98-101` (해시 함수)·11-12행(평문 미저장 원칙). ² `db_backup_dr_runbook.md`:171. ³ 같은 문서 168-169·172행. ⁴ `docs/legal/pipa_data_matrix.md`:16 원칙 — 단 프로필 결합(학교 유형+지역+학년+출생연도)의 식별 위험은 내부적으로 인지·통제 중(`db_backup_dr_runbook.md`:174).

**미성년자 관련 현행 태도.** 만 14세 미만으로 *파악된* 사용자는 법정대리인 동의가 기록되기 전까지 서비스 본 기능(코칭·진단 등 보호 엔드포인트)이 서버에서 차단된다(§2 3단계). 동의를 *기록하는* 경로는 구현되어 있으나, 그 안의 "법정대리인 본인확인"이 아직 실 구현이 아니어서(§2 5단계) **동의 기록 기능 전체를 운영 설정에서 꺼 둔 상태**다(기본 off — §2 4단계). 즉 현재는 "알려진 14세 미만은 동의 경로조차 닫혀 있어 본 기능을 이용할 수 없는" 보수적 상태이며, 이 잠금을 푸는 열쇠가 이번 자문이다.

**현재 단계.** 1인 개발·Phase 1 MVP 심화. 지인 학생 5~10명 규모의 비공개 파일럿 직전, 공개 β 이전 단계다(`docs/reviews/service_ops_mgmt_gap_review_2026-07.md`:5·80-82). 유료 결제는 미구현(무료)이다(같은 문서 25행).

### Q1. 법정대리인 본인확인 *방식*의 법적 충분성

- **ⓐ 배경**: 만 14세 미만 아동의 개인정보 처리에는 법정대리인 동의가 필요하고(개인정보보호법 §22-2 인지 — 조문 해석·시행령상 확인 방법과의 대조는 변호사 몫), 동의를 받기 전에 법정대리인 *본인 확인*이 필요하다는 것이 내부 설계 전제다(`pipa_data_matrix.md`:78 §3.2 절차 2단계). 현재 그 확인 자리는 무검증 stub이다(§2 ⑤). 후보 방식으로 휴대폰 본인인증(PASS 등)·아이핀·신용카드·이메일 회신 확인 등을 검토 대상으로 두었으나 **어느 것도 채택하지 않았다** — 각 방식의 법적 충분성 판단이 없어서다.
- **ⓑ 질문**: 개인정보보호법 §22-2 및 시행령이 정하는 법정대리인 동의 확인 방법에 비추어, ①휴대폰 본인인증(PASS 등 통신사 인증) ②아이핀 ③신용카드 인증 ④법정대리인 이메일로 동의 요청을 보내고 회신을 받는 방식 — 각각이 법적으로 충분한가? 충분한 방식이 복수라면 비용·구현 난이도 관점에서 최소 요건을 충족하는 방식은 무엇인가? 또한 "본인확인"과 별개로 그 사람이 해당 아동의 *법정대리인 지위*에 있음(친권 관계)까지 확인할 의무가 있는가, 있다면 어느 수준인가?
- **ⓒ 답변별 코드 귀결**:
  - 휴대폰 본인인증 충분 → `PhoneAuthGuardianVerifier`(가칭)를 `GuardianVerifier` 경계에 구현·주입(`consent_grant.py:77-79`가 지정한 자리). 본인인증 결과 토큰을 요청 스키마 확장 필드로 수령(`consent_grant.py:33-36` — 방식 확정 전까지 필드를 만들지 않기로 한 자리), 외부 거래 ID를 `verification_ref`에 기록(`schema/parental_consent.py:72-79`).
  - 이메일 회신 방식으로 충분 → 일회용 링크 발송·회신 확인 구현(현재 이메일은 해시만 저장하므로, 발송 목적의 평문 이메일 *일시* 취급 범위·보관 여부를 Q4·Q3과 함께 확인 필요).
  - 법정대리인 *지위* 확인까지 요구 → 가족관계 증빙 절차 설계 필요(현재 어떤 형태의 지위 확인도 없음 — 구현 규모가 크게 달라지므로 요구 수준 명시 요청).

### Q2. 출생 연도 미상 사용자의 게이트 통과 정책 + 연령 자가신고 의존

- **ⓐ 배경**: 소셜 로그인 제공자가 출생 연도를 안 주면 미성년 판정이 None이 되고, 게이트는 "*알려진* 미성년만 차단" 정책이라 **미상 사용자는 동의 없이 본 기능을 이용할 수 있다**(`consent.py:59-60`, `api/_auth.py:65-67`). "가입 시 출생 연도를 필수로 받을지"는 의도적으로 미결 정책이다(`consent.py:20-23`, `pipa_data_matrix.md`:100). 또한 출생 연도는 온보딩에서 사용자가 스스로 수정 가능한 자가신고 값이라(`api/users.py:63-68·72행`), 14세 미만이 거짓 연도를 넣으면 게이트를 피할 수 있다 — 서버는 "신고된 값" 기준으로만 보수적으로 판정한다.
- **ⓑ 질문**: ①연령 미상 사용자를 차단하지 않는 현행 설계("알려진 미성년만 차단")가 허용되는가, 아니면 연령 확인(출생 연도 필수 수집) 없이는 서비스 제공 자체를 막아야 하는가? ②연령 정보를 자가신고에 의존하는 것으로 충분한가 — 사업자에게 연령 *검증*(신고 값의 진위 확인) 의무가 어느 수준까지 있는가? ③월일 없이 연 단위만 수집해 보수적으로(만 14세일 수도 있는 사람까지) 게이트하는 현행 판정이 "만 14세 미만" 기준 이행으로 문제없는가, 생년월일 수집이 필요한가?
- **ⓒ 답변별 코드 귀결**:
  - 미상 차단 필요 → 가입/온보딩에서 birth_year 입력을 필수화(현재 nullable)하고 게이트의 None 통과 분기(`api/_auth.py:67`)를 차단으로 변경.
  - 미상 통과 허용 → 현행 유지, 단 회신 근거를 `docs/legal/`에 기록(향후 당국 문의 대비 — `regulatory_checklist.md`:34의 "근거 문서화" 방침과 동형).
  - 생년월일(월일) 수집 필요 → 스키마·판정 함수(`consent.py:43-61`) 확장 — 데이터 최소화 원칙과의 균형도 함께 질의(월일은 지금까지 *의도적으로* 안 받았다).

### Q3. 법정대리인 이메일을 해시로만 저장하는 것이 동의 *입증* 요건을 충족하는가

- **ⓐ 배경**: 미성년 PII 최소화 원칙에 따라 동의 레코드에는 법정대리인 이메일의 sha256 해시만 저장하고 평문은 저장하지 않으며, 이름·연락처는 수집 자체를 하지 않는다(`db/models/parental_consent.py:66·34-36`, `schema/parental_consent.py:55-62`). 따라서 분쟁 시 우리가 제시할 수 있는 것은 "동의 레코드 1행: 대상 학생 ID·이메일 해시·검증 방식·외부 검증 참조·범위·시각"이다(§2 ⑥ 참조 — 레코드 구조 전체가 이 표에 있다). 특정 이메일이 주어지면 해시 대조로 "그 이메일로 동의했는가"는 확인 가능하지만, 레코드에서 역으로 "누가" 동의했는지 평문으로 복원할 수는 없다. 참고로 내부 기술 표준 문서의 초기 설계(`docs/standards/security_privacy.md`:30-35)는 법정대리인 PII를 *암호화 저장*(`guardian_pii_encrypted`)하는 안이었으나, 실제 구현은 그보다 더 축소해 **수집 자체를 하지 않는** 쪽을 택했다 — 이 선택이 입증 관점에서 유지 가능한지가 본 질문이다.
- **ⓑ 질문**: 동의 획득 사실의 입증(사업자의 증명 책임) 관점에서, ①해시+검증 방식+외부 거래 참조만으로 충분한가? ②실 본인확인 도입 시(예: 휴대폰 인증) 본인인증 기관 측 거래 기록과 우리 측 `verification_ref`의 대조로 입증이 성립하는가? ③아니면 법정대리인 성명·연락처 등 평문(또는 복호 가능한 암호화 저장)을 일정 기간 보관해야 하는가 — 보관해야 한다면 항목·기간·저장 방식(암호화 요건)은?
- **ⓒ 답변별 코드 귀결**:
  - 현행 충분 → 변경 없음(회신 근거 문서화만).
  - 검증 기관 거래 기록과의 대조로 충분 → 실 구현 시 `verification_ref` 기록을 필수화(현재 nullable — `db/models/parental_consent.py:70`)하고 검증 기관의 기록 보존 기간을 계약으로 확인.
  - 평문/복호 가능 보관 필요 → 봉투 암호화 저장 필드 신설(기존 대화 암호화 프리미티브 재사용 — `db_backup_dr_runbook.md`:168 참조) + 보존 기간·파기 절차를 privacy 모듈에 연결. 이는 초기 설계(`security_privacy.md`:34)로의 부분 회귀이므로 항목·기간을 최소로 특정해 주기를 요청.

### Q4. 동의의 범위(scope)·만료·재동의 주기

- **ⓐ 배경**: 동의 범위는 현재 `service_core`(서비스 본 기능 이용) **단일 값**이다 — 모델 학습 활용·제3자 제공·마케팅 등은 "변호사 자문으로 문구·범위가 확정된 뒤 추가"하기로 하고 의도적으로 만들지 않았다(`schema/enums.py:1115-1131`). 만료는 필드(`expires_at`)만 있고 **항상 None으로 기록**되며, 게이트가 만료를 재차단하지도 않는다(`api/users.py:235`, `pipa_data_matrix.md`:110 미구현 항목 ②). 내부 표준 문서에는 "매 분기 재확인"이라는 잠정 문구가 있으나(`security_privacy.md`:6) 적정 주기는 변호사 검토 사항으로 유보되어 있다(`pipa_data_matrix.md`:71) — **문서의 잠정치와 구현(만료 없음) 사이에 간극이 있는 상태**다. 동의 시 고지 의무(수집 항목·목적·보유 기간·제3자 제공 여부)는 설계 방향으로만 있고(`pipa_data_matrix.md`:84), 실제 고지 문구·화면은 미구현이다.
- **ⓑ 질문**: ①법정대리인 동의에 유효기간·주기적 재확인이 법적으로 요구되는가? 요구되지 않는다면 "만료 없음 + 철회권 보장"으로 충분한가, 요구된다면 적정 주기는? ②동의 범위를 "서비스 본 기능 이용" 하나로 묶은 현행 단위가 적정한가, 수집 항목·목적별로 더 쪼개야 하는가? ③동의 시 고지해야 할 사항(항목·목적·보유 기간·제3자 제공)의 문구를 검토·작성해 줄 수 있는가(고지 화면 구현의 입력물)?
- **ⓒ 답변별 코드 귀결**:
  - 만료 필요(주기 N) → GRANT 시 `expires_at = 동의 시각 + N` 기록(`api/users.py:235`의 None을 교체) + 게이트에 만료 재차단 분기 추가(`api/_auth.py:67` 조건 확장) + 재확인 요청 플로우 설계.
  - 만료 불요 → 현행 유지·근거 문서화. `security_privacy.md`:6의 "매 분기 재확인" 잠정 문구를 회신에 맞게 정정.
  - 범위 세분화 필요 → `ConsentScope`에 값 추가(enum은 확장 대비 설계 완료 — DB는 문자열 저장이라 마이그레이션 불요, `schema/enums.py:1127-1128`) + 범위별 동의 레코드 분리 수령.
  - 고지 문구 확보 → 동의 화면(법정대리인 대면 UI — Q7과 연동) 구현의 선행 입력물로 사용.

### Q5. 비공개 파일럿(지인 5~10명) 단계에서 요구되는 수준

- **ⓐ 배경**: 서비스는 파일럿 직전이다. 내부 검토 문서는 "파일럿(지인 학생·소규모)은 현 동의 게이트로 진행 가능하나 공개 β 전 MGMT-01 완료 필수"라고 *관측*했으나(`service_ops_mgmt_gap_review_2026-07.md`:81), **이는 내부 판단일 뿐 법적 확인을 받은 바 없다**. 파일럿 예상 구성: 지인 학생 5~10명, 무료, 비공개(모집 광고 없음). 대상 학생은 중·고생이므로 대부분 14세 이상일 것이나 확정은 아니다. 현행 상태에서 파일럿을 하면: 14세 미만 참가자는 (a) 동의 경로가 꺼져 있어 이용 불가이거나(§2 ④) (b) 출생 연도 미상이면 동의 없이 이용하게 된다(§2 ③·Q2).
- **ⓑ 질문**: ①이 규모·성격의 비공개 파일럿에서 14세 미만 참가자가 있을 경우, 실 본인확인 구현 *전에* 어떤 대체 절차(예: 서면/대면으로 보호자 동의서 수령 후 운영자가 수동으로 동의 기록)로 진행 가능한가? ②그 대체 절차가 가능하다면 갖춰야 할 최소 요건(동의서 문구·보관·본인확인 수준)은? ③아니면 파일럿 대상을 "14세 이상 확인된 학생"으로 한정하는 것이 안전한가 — 그 경우 확인 방법의 요구 수준은? ④파일럿이어도 개인정보 처리방침·수집 동의(14세 이상 본인 동의 포함)는 갖춰야 하는가(Q6과 연동)?
- **ⓒ 답변별 코드 귀결**:
  - 수동 대체 절차 허용 → 운영자 수동 동의 기록 경로 설계(현행 엔드포인트는 학생 세션 전용이므로 별도 관리 절차 필요 — 단 이것도 회신의 요건을 반영해 설계) + `verification_method`에 해당 방식명 기록(예: "manual_paper" — 값은 회신 후 확정).
  - 14세 이상 한정 권고 → 파일럿 온보딩에서 출생 연도 입력을 필수 운영(코드 변경 없이 운영 절차로 가능한지 포함해 설계) + 참가자 선별 기준 문서화.
  - 파일럿에도 처리방침 필요 → Q6 ⓒ의 약관·처리방침 작업을 파일럿 전으로 앞당김.

### Q6. 14세 *이상* 미성년(중·고생 대부분)에 대한 요건 — 본인 동의·고지·약관

- **ⓐ 배경**: 주 이용자인 중·고생 대부분은 14세 이상 미성년이다. 내부 설계는 "14세 이상은 본인 동의 + 데이터 사용 명시적 통지"로 방향만 잡혀 있다(`pipa_data_matrix.md`:88-91 §3.3, `security_privacy.md`:10-12). **실측**: 이용약관·개인정보처리방침·수집 동의 화면은 백엔드·모바일 소스에서 검색 무일치 — 구현이 없다(2026-07-27 `src/` 전체 검색, 관련 코드 0건). 내부 규제 체크리스트에도 "가입 전 약관·처리방침 제공·동의 절차"가 미완 항목으로 등재되어 있다(`docs/legal/regulatory_checklist.md`:74).
- **ⓑ 질문**: ①14세 이상 미성년의 개인정보 수집·이용 동의는 본인 동의만으로 충분한가, 항목·목적에 따라 법정대리인 동의가 추가로 필요한 경우가 있는가(예: 향후 유료 결제·마케팅 동의)? ②미성년자와의 서비스 이용 계약(약관 동의) 자체의 유효성 관점에서 법정대리인 관여가 필요한 지점이 있는가? ③가입 전 제공해야 할 고지·동의 문서(약관·처리방침) 작성을 자문 범위에 포함할 수 있는가?
- **ⓒ 답변별 코드 귀결**:
  - 본인 동의로 충분 → 가입 온보딩에 동의 화면 추가(문구는 회신 산출물 사용) — 동의 사실 기록 필드 신설.
  - 특정 항목에 법정대리인 동의 추가 필요 → 해당 항목을 `ConsentScope` 확장 값으로 분리(Q4 ⓒ와 동일 기제)하고 14세 이상에도 해당 scope의 보호자 동의 경로 적용.
  - 약관·처리방침 작성 수임 → 산출물을 `docs/legal/`에 정본화하고 가입 플로우 구현의 입력물로 사용.

### Q7. (조사 중 발생) 법정대리인 *인증 모델* — 학생 세션에서 동의가 제출되는 현행 구조

- **ⓐ 배경**: 현행 동의 기록 엔드포인트는 **동의 대상 학생 본인으로 인증된 세션**에서 호출된다(`api/users.py:178`·`schema/parental_consent.py:112` "동의 대상 학생은 인증 세션에서 정해진다"). 즉 실 본인확인을 붙이더라도, 구조상 "학생의 기기·학생의 로그인 상태에서 보호자가 (기기를 건네받아) 본인확인·동의를 수행"하는 흐름이 기본형이 된다. 보호자 전용 계정·일회용 링크 등 별도 인증 모델은 의도적 후속 설계로 남겨져 있다(`consent_grant.py:17-21`).
- **ⓑ 질문**: ①동의의 의사표시가 *아동의 인증 세션*을 매개로 수집되는 구조 자체에 법적 문제가 있는가 — 본인확인(예: 보호자 명의 휴대폰 인증)이 그 세션 안에서 이뤄진다면 충분한가? ②아니면 보호자에게 *별도 채널*(보호자 이메일/휴대폰으로 발송된 링크에서 동의)로 의사표시를 받아야 하는가? ③채널 요건이 있다면 최소 형태(일회용 링크로 충분한가, 보호자 계정 가입까지 필요한가)는?
- **ⓒ 답변별 코드 귀결**:
  - 학생 세션 내 본인확인으로 충분 → 현행 엔드포인트 구조 유지, verifier만 교체(§4의 최소 경로).
  - 별도 채널 필요 → 보호자 대상 링크 발송·별도 미인증 동의 페이지·토큰 검증 플로우 신설(엔드포인트 구조 변경 — 구현 규모가 크게 달라지므로 요건 수준의 명확화 요청). 발송을 위한 보호자 연락처 평문 취급 범위는 Q3와 함께 확정.

### Q8. (조사 중 발생) 동의 *철회* 처리 절차와 백업 잔존

- **ⓐ 배경**: 철회 시각 필드(`revoked_at`)는 있으나 철회를 접수·처리하는 절차는 미구현이고, "철회 시 데이터 처리 절차는 변호사 자문" 사항으로 유보되어 있다(`schema/parental_consent.py:98-101`, `pipa_data_matrix.md`:86). 한편 계정 삭제(잊힐 권리) 처리 후에도 DB 백업 파일 안에는 해당 데이터가 보존 기간(기본 14일)만큼 잔존하는 구조이며, 이 잔존 창은 내부적으로 인지·문서화되어 있다(`db_backup_dr_runbook.md`:180).
- **ⓑ 질문**: ①법정대리인이 동의를 철회하면 아동 데이터 처리는 어떤 순서·기한으로 이뤄져야 하는가(즉시 이용 중지 + 파기? 파기 유예 허용?) ②철회 시에도 동의 *이력*(감사 레코드)은 보존 가능한가 — 가능하다면 기간은? ③삭제·철회 후 백업 내 최대 14일 잔존이 파기 의무 이행과 양립하는가, 잔존 창을 파기 안내에 고지하면 충분한가?
- **ⓒ 답변별 코드 귀결**:
  - 즉시 파기 요구 → 철회 접수 시 기존 privacy 삭제 파이프라인(`src/backend/whymath_backend/privacy/` — 삭제·열람·보존 CLI 기구현, `service_ops_mgmt_gap_review_2026-07.md`:54) 호출로 연결 + `revoked_at` 기록 + 게이트 재차단.
  - 유예 허용 → 유예 기간을 설정값으로 두고 게이트만 즉시 차단.
  - 잔존 창 고지로 충분 → 파기 안내 문구에 백업 잔존 창을 명시(런북 §4-3의 기존 방침 유지)·회신 근거 문서화.

## 4. 자문 회신 → 구현 매핑

회신이 오면 코드가 어디서 어떻게 바뀌는지의 지도다. **원칙: 변호사 회신 전에는 실 본인확인 구현에 착수하지 않는다** — 방식이 확정되지 않은 채 만든 구현은 "가짜 검증" 위험이 있고, 그래서 요청 스키마의 방식별 입력 필드조차 지금 만들지 않았다(`consent_grant.py:33-36`).

| 회신 항목 | 바뀌는 곳 (실측 seam) | 내용 |
|---|---|---|
| 본인확인 방식 확정 (Q1) | `consent_grant.py:69-84` `GuardianVerifier` Protocol — 실 구현 클래스를 만들어 `_default_guardian_verifier`(`consent_grant.py:111-117`) 주입을 교체. 주입 지점은 `api/users.py:52-54`(FastAPI 의존성) | **엔드포인트·테이블·게이트는 불변** — 이 경계 하나만 바꾸도록 설계돼 있다(`consent_grant.py:77-79`). 방식별 입력(인증 토큰 등)은 `GuardianVerificationRequest`(`consent_grant.py:30-43`)에 확장 필드로 추가. 검증 방식명이 `verification_method`, 외부 거래 ID가 `verification_ref`로 기록된다(`api/users.py:231-232`) |
| 동의 경로 활성화 | 설정 키 `WHYMATH_PARENTAL_CONSENT_GRANT_ENABLED` (`config.py:456-467`, 기본 False) | 실 verifier 결선 *후에만* on — stub 상태로 켜는 것은 self-consent 우회 경로라 금지(같은 곳 문서화) |
| 연령 기준 변경 시 (Q2) | 설정 키 `WHYMATH_MINOR_CONSENT_AGE` (`config.py:445-455`, 기본 14) + 미상 통과 분기 `api/_auth.py:67` + birth_year 필수화 여부(스키마·온보딩) | 기준 연령은 설정 한 곳(`config.py:441-442` — 가입·수정 경로 공유), 미상 정책은 게이트 분기 |
| 만료·재동의 (Q4) | `api/users.py:235`(expires_at=None → 정책값) + `api/_auth.py:67`(만료 재차단 분기 추가) | 필드·인덱스는 준비 완료(`db/models/parental_consent.py:75·83-89`) — 정책값과 재확인 플로우만 추가 |
| 동의 범위 확장 (Q4·Q6) | `schema/enums.py:1115-1131` `ConsentScope`에 값 추가 | DB는 String(32) 저장이라 값 추가에 마이그레이션 불요(`schema/enums.py:1127-1128`·`db/models/parental_consent.py:24-25`) |
| 입증 자료 보강 (Q3) | `verification_ref` 필수화 또는 암호화 보관 필드 신설(`db/models/parental_consent.py:70` 인근) | 회신의 보관 항목·기간에 따름 |
| 보호자 별도 채널 (Q7) | 신규 플로우(엔드포인트 구조 변경) — 현행 seam 범위 밖 | 회신이 요구할 때만 별도 태스크로 설계 착수 |
| 철회 절차 (Q8) | `revoked_at` 기록 경로 신설 + `privacy/` 삭제 파이프라인 연결 | 회신의 순서·기한에 따름 |

**후속 태스크 연결**: 위 각 행은 MGMT-01의 acceptance(①변호사 자문 ②자문 기반 verifier 실구현 교체 ③PII 최소수집·해시 원칙 유지 — `backlog/tasks/MGMT-01-guardian-real-verification.yaml`:13-16)에 대응한다. 자문 회신(①) 완료 후, 구현(②)은 회신 내용을 반영한 별도 구현 태스크로 backlog에 등재해 진행한다. ③은 회신이 평문 보관을 요구하지 않는 한 모든 구현에서 유지한다.
