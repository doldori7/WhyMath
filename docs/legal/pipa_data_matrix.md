# PIPA 데이터 권한 매트릭스 — WhyMath

> **출처**: MathScope PRD v1.1 §11.3(데이터 권한 매트릭스)을 WhyMath 골격에 통합. PRD의 "MathScope" 표기는 "WhyMath"로 치환.
> **PIPA** = 개인정보보호법(Personal Information Protection Act).
>
> ⚠️ **법률 단정 금지**: 이 문서는 *제품 설계 기준*이며 법률 자문이 아니다. 14세 미만 동의 절차·민감정보 분류·국외 이전·ISMS-P 적용 범위 등 *모든 컴플라이언스 판단은 변호사·개인정보 전문가 자문을 거쳐 확정*한다. 본 문서에서 "**변호사 자문 필수**"로 표기된 항목은 시행 전 반드시 검토.
>
> **자매 문서**: 보안·암호화·PII 분리 저장의 *기술 표준*은 `docs/standards/security_privacy.md`. 이 문서는 *누가 어떤 데이터를 어디까지 볼 수 있는가*의 권한 설계를 다룬다. 둘은 함께 읽는다.

---

## 1. 설계 원칙

WhyMath는 미성년자의 학습 데이터를 다룬다. CLAUDE.md 절대 금기·의사결정 우선순위(1번 학생 안전, 2번 법적·윤리적 준수)에 따라, 데이터 접근은 **"필요 최소 + 역할별 차등 + 학생 본인 우선"** 원칙으로 설계한다.

- **데이터 최소 수집**: 학습 코칭에 *불필요한* 데이터는 수집하지 않는다.
- **역할별 차등 노출**: 같은 데이터라도 학생/교사/부모가 보는 *해상도*가 다르다.
- **학생 본인 우선**: 학생은 자기 데이터에 대해 가장 넓은 접근권을 가진다. 부모·교사 노출은 *학생의 학습을 돕는 범위*로 한정.
- **비교 데이터 보호**: 또래 비교·순위 정보는 *정서적 위해* 가능성(CLAUDE.md "우열 게임화 금지") 때문에 가장 엄격히 통제.

## 2. 데이터 권한 매트릭스 (PRD §11.3)

### 2.1 범례

| 기호 | 의미 |
|---|---|
| ● | **전체 공개** — 원자료·상세 수준까지 접근 |
| ◐ | **요약만** — 집계·추세·등급 등 가공된 형태만, 원자료 비공개 |
| ✕ | **미공개** — 접근 불가 |

### 2.2 매트릭스 (학생 / 교사 / 부모 × 9개 데이터 항목)

> "교사"는 Phase 3+ B2B 학원·학교 맥락의 *담당 강사/교사*를 의미한다(`business_model.md` §3~4). Phase 1~2 B2C 단계에서는 교사 열이 적용되지 않는다.

| # | 데이터 항목 | 학생 본인 | 교사 (B2B) | 부모 | 설계 메모 |
|---|---|:---:|:---:|:---:|---|
| 1 | **정답률** | ● | ● | ◐ | 부모에게는 *추세·등급*으로. 절대 수치 압박 완화 |
| 2 | **풀이 시간** | ● | ◐ | ◐ | 교사·부모에게 원자료 노출 시 "느리다" 압박 → 요약만 |
| 3 | **오답 패턴** | ● | ◐ | ✕ | 교사는 *지도용 요약*. 부모 미공개 — 오답 상세는 정서 위해·낙인 위험 |
| 4 | **이용 시간대** | ● | ✕ | ◐ | 교사 불필요. 부모는 *생활 관리* 목적 요약(예: 주로 저녁 학습) |
| 5 | **숙달 개념** | ● | ● | ◐ | "잘하는 것"은 비교적 안전 → 교사 전체, 부모 요약 |
| 6 | **빈틈 개념** (미숙달) | ● | ◐ | ◐ | "못하는 것"은 민감 → 교사·부모 모두 *지도/지원용 요약*만, 낙인 방지 |
| 7 | **강사 코멘트** | ● | ● | ◐ | 학생 본인이 받은 피드백은 전부 봄. 부모는 요약(맥락 없는 노출 방지) |
| 8 | **또래 비교** | ◐ | ◐ | ✕ | 학생 본인도 *요약만*(과도한 순위 의식 차단). **부모 미공개** — CLAUDE.md "우열 게임화 금지"의 직접 적용 |
| 9 | **힌트 사용** (Polya 단계별 힌트 사용 이력) | ● | ◐ | ✕ | 학생은 자기 학습 패턴 인지. 교사 요약. 부모 미공개 — "힌트 많이 썼다 = 못한다"는 *오해 위험* |

### 2.3 매트릭스 해석의 핵심

- **부모 열에 ✕·◐가 많은 이유**: 부모의 *불안*이 학생에게 *압박*으로 전이되는 것을 막기 위함. WhyMath는 부모에게 "감시 도구"가 아니라 "*지원 도구*"를 제공한다. 부모 보고서는 *진척·강점 중심*으로 구성하고, 오답·또래 비교·힌트 사용 같은 *위해 가능 데이터*는 노출하지 않는다.
- **교사 열이 ◐ 중심인 이유**: 교사는 *지도*에 필요한 만큼만 본다. 원자료(개별 풀이 시간·오답 상세)는 학생 본인의 것.
- **또래 비교(#8)가 가장 엄격한 이유**: CLAUDE.md "학습 시간·정답률만으로 우열을 매기는 게임화 금지", "부정적 피드백을 정서적으로 강화하는 표현 금지"의 직접 구현. 학생 본인조차 ◐(요약만), 부모는 ✕.
- 이 매트릭스는 `docs/standards/security_privacy.md`의 "부모에게 *불필요한* 학생 PII 노출 금지"를 *데이터 항목 수준으로 구체화*한 것이다.

### 2.4 적용 시 주의

- 위 권한은 *기본값*이다. 학생(14세 이상) 또는 법정대리인이 *명시적으로* 더 넓은 공개를 선택할 수 있으나, 그 경우에도 또래 비교(#8) 부모 공개는 *제품 차원에서 차단*한다(정책적 결정).
- 매트릭스의 각 칸을 코드의 *권한 체크 단위*로 사용한다(L2 학습자 모델 + 횡단 권한 레이어). 새 데이터 항목 추가 시 *반드시* 이 매트릭스에 행을 추가하고 변호사 검토를 거친다.

## 3. 14세 미만 법정대리인 동의

> ⚠️ **변호사 자문 필수** — 아래는 제품 설계 방향이며, 동의 방식·연령 기준·재확인 주기의 법적 적정성은 전문가 검토로 확정.

### 3.1 원칙

- **14세 미만**: 회원가입·개인정보 처리에 **법정대리인(부모/보호자)의 동의 필수**. `docs/standards/security_privacy.md`의 "14세 미만 부모 동의 미들웨어"와 동일한 요구사항.
- 동의 없이 14세 미만의 서비스 본 기능 이용 불가(가입 단계에서 차단).
- 동의는 *가입 시 1회로 끝나지 않고* 주기적 재확인(`security_privacy.md`: 매 분기 재확인 — 적정 주기는 변호사 검토).

### 3.2 동의 절차 설계 방향

```
14세 미만 가입 시도
   ├─ 1. 연령 확인 (생년월일 입력)
   ├─ 2. 법정대리인 정보 입력 → 법정대리인 본인 확인 절차
   ├─ 3. 법정대리인에게 동의 요청 (수집 항목·목적·보유기간 고지)
   ├─ 4. 법정대리인 동의 완료 → parental_consents 레코드 생성 (암호화 저장)
   └─ 5. 동의 만료 시 재확인 요청, 미재확인 시 기능 제한
```

- 동의 시 *수집 항목·이용 목적·보유 기간·제3자 제공 여부*를 명확히 고지(PIPA 고지 의무).
- `docs/standards/security_privacy.md`의 `parental_consents` 테이블 구조와 연동 — `consent_signed_at`, `expires_at`, `guardian_pii_encrypted`.
- **검토 필요 사항(변호사 자문 필수)**: 법정대리인 본인 확인 방식(휴대폰 인증·아이핀 등 중 무엇이 적정한지), 동의 재확인 주기, 동의 철회 시 데이터 처리 절차.

### 3.3 14세 이상

- 본인 동의(PIPA). 데이터 사용을 *명시적으로* 통지.
- 단, 미성년자임에는 변함이 없으므로 §2 권한 매트릭스의 *부모 노출 제한*은 14세 이상에도 동일 적용(또래 비교 부모 미공개 등).

### 3.4 구현 현황 — 서버측 `is_minor` 파생(P4, 2026-06)

> 동의 *게이트*는 이미 존재했으나(미성년이면서 동의 없으면 보호된 엔드포인트 403), `is_minor`가 서버에서 정해지지 않아 무력했다. 이를 닫은 *게이트 실효화* 작업의 현황이다. **동의 *획득(GRANT)* 플로우·`parental_consents` 테이블은 여전히 미구현**(아래 — 변호사 자문 필수).

- **구현됨**: `is_minor`는 이제 회원 프로필의 모든 쓰기 경로(가입 OAuth 콜백·`PATCH /v1/users/me`)에서 `birth_year`로부터 *서버측 파생*된다(`backend/whymath_backend/consent.py`). 클라이언트가 보낸 `is_minor`는 신뢰하지 않는다(직접 수정 불가 + 매 쓰기마다 서버값으로 덮어씀) — 미성년이 `is_minor=false`로 게이트를 우회할 수 없다.
- **연령 기준**: `minor_consent_age`(기본 14·`Settings`)로 설정. PIPA 만14세 미만(§3.1)을 반영하되, 법정 기준의 *법적 적정성 자체는 §3.1 단서대로 변호사 자문으로 확정*한다.
- **보수적 연나이(year-reckoning)**: 생일(월일)을 수집하지 않고 `birth_year`만 받으므로(데이터 최소화·§1), 정확한 만나이 대신 *연나이*(`현재연도 − 출생연도`)로 판정하며 연나이가 임계와 *같을 때까지* 미성년으로 본다(과보호). 근거: 연나이 14는 생일 전이면 실제 만13세일 수 있어, *진짜 만13세를 게이트하지 않는 위반*보다 *만14세를 게이트하는 약간의 마찰*을 택한다(의사결정 우선순위 1 학생 안전·2 법적 준수 > 5 UX). **정확한 만나이 게이팅(생일 수집)·자가신고 연령의 신원 확인 방식은 변호사 자문 필수**(§5 체크리스트와 연계).
- **미구현(후속·변호사 자문 필수)**: ① 법정대리인 동의 *획득* 플로우(§3.2 절차 2~5단계)와 ② `parental_consents` 테이블(`security_privacy.md` 연동)은 *아직 만들지 않았다* — 동의 방식·본인 확인·재확인 주기의 법적 적정성 검토가 선행 조건이다(§3.1·§3.2 단서). 현재는 동의 *상태*(`parent_consent_at`)를 *읽어 게이트만 걸* 뿐, 동의를 *받는* 경로는 없다. ③ 가입 시 `birth_year`를 *필수로 받을지*도 별도 정책 결정이다(현재는 미상이면 `is_minor=None`으로 게이트를 통과시킨다 — *알려진* 미성년만 차단).

## 4. ISMS-P 인증 추진

> ISMS-P = 정보보호 및 개인정보보호 관리체계 인증.

### 4.1 추진 방향

- WhyMath는 미성년자 개인정보를 대량으로 다루므로, **ISMS-P 인증 추진을 중장기 컴플라이언스 목표로 설정**한다.
- 인증은 *공적 신뢰*(B2B 학교·교육청 진입 시 자산, `business_model.md` §4)와 *내부 보안 규율* 두 측면에서 가치.

### 4.2 단계적 접근 (가설)

| 시점 | 활동 | 비고 |
|---|---|---|
| Phase 1~2 | `docs/standards/security_privacy.md` 표준 *실제 구현* — PII 분리 저장·암호화·감사 로그 | 인증의 *기반 공사* |
| Phase 2 종료 시 | 보안 감사 1회(`security_privacy.md` 침투 테스트와 연계) | 인증 전 자가 점검 |
| Phase 3~4 | ISMS-P 인증 *의무 대상 여부* 검토 → 대상이면 인증 준비 본격화 | **변호사·인증 전문가 자문 필수** — 매출·이용자 수 기준의 의무 대상 여부 판단 |
| B2B 본격화 시점 | 인증 취득 목표 | B2B 학교·교육청 계약의 신뢰 요건 |

> ISMS-P *의무 대상*인지 여부는 매출액·이용자 수 등 법정 기준에 따른다. WhyMath가 의무 대상이 되는 시점은 성장 속도에 달려 있으므로, **Phase 2~3 시점에 의무 대상 여부를 전문가와 함께 판정**하고 그에 맞춰 일정을 확정한다. 의무 대상이 아니더라도 *자율 취득*은 B2B 신뢰 자산으로 검토.

## 5. 변호사·전문가 자문 필요 사항 (체크리스트)

- [ ] 14세 미만 법정대리인 *본인 확인 방식*의 법적 적정성 → **변호사 자문 필수**
- [ ] 법정대리인 동의 *재확인 주기*의 적정성 → **변호사 자문 필수**
- [ ] 9개 데이터 항목 중 *민감정보(PIPA)에 해당*하는 것이 있는지 분류 → **변호사 자문 필수**
- [ ] 학습 데이터의 *모델 학습 활용* 시 별도 동의 범위·방식 → **변호사 자문 필수** (CLAUDE.md "동의 없이 학습 사용 금지"와 연계)
- [ ] 부모 보고서 제공이 *제3자 제공*에 해당하는지 여부(법정대리인이라도 검토) → **변호사 자문 필수**
- [ ] ISMS-P *의무 대상 여부* 및 취득 시점 → **인증 전문가 자문 필수**
- [ ] 데이터 보유 기간·파기 절차의 법정 요건 부합 여부 → **변호사 자문 필수**
- [ ] B2B 학원·학교 계약 시 데이터 *처리 위탁/제공* 관계 정리 → **변호사 자문 필수** (`business_model.md` §7과 중복 — 통합 검토)
